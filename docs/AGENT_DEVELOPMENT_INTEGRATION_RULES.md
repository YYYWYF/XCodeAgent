# 智能体开发流程集成规范

> 状态：强制执行
> 生效日期：2026-08-27
> 适用范围：XCodeAgent 中所有业务智能体需求、设计、协议、工作流、前后端、UI、测试、文档和配置变更

## 1. 目标与红线

智能体开发能力必须作为现有应用开发主流程中的正式产物集成，不得破坏、替换或绕过当前页面/API/实体开发能力。

以下规则为硬约束：

1. 不新增平行顶层工作流、第二套工作台、第二套聊天框架、第二套测试/审查/验收链路或第二套状态事实源。
2. `prototype/` 只提供交互意图、状态和用户旅程参考，不是生产代码、生产 schema、目录结构或技术栈的权威来源。
3. 能复用现有组件、Hook、Service、领域类型、AG-UI 协议、生命周期、Build DAG、Diff、Preview、测试和验收能力时必须复用。
4. 每个开发批次只能实施获得用户确认的最小闭合范围；不得顺带重构、迁移旧数据、修复无关问题或引入新依赖。
5. 任何既有页面/API/实体流程的行为、协议、UI 和验证证据都属于回归基线；智能体能力不得改变其默认路径。

## 2. 开发前强制流程

### 2.1 文档阅读门禁

首次基于一个新代码基线开展正式智能体集成前，必须完整阅读 `docs/` 下全部既有文档，并建立“文档约束 → 本批次影响 → 冲突 → 验证”的映射。之后每个批次至少重新阅读：

- `docs/CODEBASE_INDEX.md`；
- 本规范与 [智能体开发流程实现状态](./AGENT_DEVELOPMENT_IMPLEMENTATION_STATUS.md)；
- [智能体开发原型集成说明](./AGENT_PROTOTYPE_INTEGRATION.md)；
- 本批次触及领域在索引中标记的所有文档；
- 自上次审查后发生变化的其他 `docs` 文件。

“已阅读全部文档”不等于“全部文档具有相同权威级别”。必须按以下类别处理：

| 类别 | 用法 |
| --- | --- |
| 当前代码事实与 Codebase Index | 用于确认当前真实入口、数据流、文件归属和已实现边界。 |
| 标记为 Canonical、唯一权威或强制规则的文档 | 作为对应领域的正式设计与约束。 |
| 当前实现计划/状态文档 | 用于确认已完成、在途和未完成边界。 |
| To-Be、推荐方案、评审、审计、旧流程或历史设计 | 必须吸收仍适用的约束与风险，但不得直接覆盖当前契约。 |
| 原型说明与原型代码 | 用于理解用户旅程和交互，不作为生产实现方案。 |

发现文档之间、文档与代码之间或原型与当前契约之间存在矛盾时，必须在计划中明确列出，并在写代码前请求用户裁决；不得静默选择、拼接多套方案或用兼容分支同时保留。

### 2.2 现状核对

每个批次开始时必须执行只读核对：

1. 查看 `git status --short`，保留用户已有改动。
2. 通过 `docs/CODEBASE_INDEX.md` 定位最小文件集，再读取相关生产代码和测试。
3. 对照 `prototype/` 确认要吸收的交互意图，以及明确不复制的 Mock、硬编码和旧技术假设。
4. 记录既有 API、AG-UI 事件、Graph 节点、生命周期、artifact、会话、UI 和测试路径。
5. 建立当前功能回归基线，区分“已验证”“仅代码存在”“原型存在”和“未实现”。

### 2.3 计划与确认门禁

开始编辑前必须提交详细计划，至少包含：

- 需求理解与本批次完成定义；
- 明确在范围内和不在范围内的内容；
- 逐文件修改位置与复用点；
- 数据、类型、API、AG-UI、Graph、生命周期和 UI 的端到端流转；
- 与当前代码、文档和原型的冲突及解决建议；
- 对既有页面/API/实体/自由对话流程的回归风险；
- 自动化、Electron 运行态、明暗主题、安全和失败路径验证；
- 回滚或停止条件。

只有用户明确确认该计划后才能修改文件。确认只授权计划列出的范围；发现新的架构决策、公开契约变化、高风险操作或超出范围的冲突时，必须停止并再次确认。

## 3. 当前主流程基线

智能体能力必须嵌入当前正式链路，而不是按照原型自建链路：

```text
RequirementSpec + ProductPlan 联合确认
  -> UiDesign 确认或明确跳过
  -> 用户显式进入规划阶段
  -> TechnicalPlan 确认
  -> 模板物化与工作台就绪
  -> development_readiness_gate
  -> inspect_workspace
  -> prepare_build_tasks
  -> Build DAG 显式确认
  -> build
  -> unit_test / unit_test_repair
  -> 测试阶段显式确认
  -> integration_test / small_task_repair
  -> 审查阶段显式确认
  -> code_review / code_review_repair
  -> 验收阶段显式确认
  -> launch_project / acceptance_review
  -> 用户验收与完成
```

智能体加入后的具体 Artifact DAG、字段 owner、运行时位置和 Build Unit 必须先形成正式设计并确认。尚未决定的部分不得从原型的 `ProjectPlan` 文案、Python 文件路径或 Mock AG-UI 事件中推断。

## 4. 正式产物与确认规则

1. 任何会被下游消费的智能体正式产物，在生成或修改后都必须停止并等待显式用户确认。
2. RequirementSpec 与 ProductPlan 继续遵循仓库规定的联合确认例外；智能体不得借此绕过 UiDesign、TechnicalPlan 或后续确认门。
3. 澄清回答、自然语言“继续”、保存草稿、预览成功、配置卡片或代码已生成均不等于确认。
4. 用户可见正式产物使用 Markdown；JSON 仅作为内部结构化状态。确认 Markdown 时必须把用户修改同步回内部 JSON，并保留隐藏结构化信息。
5. 每个 artifact、配置候选和下游引用必须使用稳定 ID、revision/hash 与 `basedOnRevision`；旧卡片、重复提交和上游已变化的确认必须拒绝。
6. 上游变更只使受影响的下游失效；失效范围必须由确定性规则计算，不能由模型自行决定或通过目录是否存在推断。
7. 当前契约只支持当前 storage/schema；除非用户在同一任务明确要求，不添加迁移、旧字段读取、fallback alias、双写或兼容分支。

## 5. 工作流与 AG-UI 规则

1. 所有新增或实质变化的产品动作必须端到端使用 AG-UI，不得新增普通 JSON/REST 产品接口、手写 `fetch`、自定义 SSE 或手工事件 parser。
2. 每个独立 AG-UI action/flow 必须具有完整生命周期：run start、assistant message、结构化 result/error、state snapshot/delta 和唯一 terminal event。
3. 正常业务失败必须有稳定错误码、可恢复动作和安全消息；未捕获异常使用错误终态，不得伪装成功完成。
4. Graph 负责阶段、路由、确认、质量门和恢复；Agent 只在授权任务范围内推理和执行，不得自行推进 lifecycle、修改正式计划或宣布验收通过。
5. 大型源码、日志、知识内容、模型原文和 Diff 落盘并以有界引用传递；Graph State 与 AG-UI 快照只保存必要摘要、ID、hash 和路径引用。
6. 新增智能体事件优先映射现有标准事件与通用投影；确需自定义事件时必须有版本化类型、前后端严格类型、未知类型 fallback 和重放测试。
7. 智能体会话、阶段、target、run 和 thread 必须与页面/API/实体一样隔离，不能复用其他目标的确认、候选配置或验收状态。

## 6. 设计、配置与版本规则

1. 原型中的十部分设计结构可作为内容候选：任务目标、行为规则、边界限制、输入、输出、模型、对话体验、记忆、工具和知识；正式字段、归属和 schema 必须另行确认。
2. 配置至少区分 `active`、`draft` 和 `candidate`：
   - `active` 是当前已验收生效版本；
   - `draft` 是用户编辑但未提交的工作副本；
   - `candidate` 是已确认变更并已生成代码、等待验证或验收的候选。
3. 配置变更固定走“确认配置变更 → 重新生成 → 审阅真实 Diff → 运行 required checks → 启动/试聊 → 智能体验收 → 激活候选”。
4. candidate 验收前不得影响 active 的 Markdown、源代码、工具适配、页面调用、左侧对话或真实试聊；失败时保留证据并允许继续修复或放弃候选。
5. 当前未发布版本可以按正式变更流程编辑；已发布版本和历史版本只读。需要变化时创建新候选版本，不原地覆盖历史。
6. 页面调用智能体必须使用稳定引用，并通过已确认的页面行为、API、实体和权限契约编译；不得按名称模糊匹配或在 UI 内硬编码关系。

## 7. 代码、UI 与复用规则

1. 先复用现有领域类型、组件、Hook、Service、状态 reducer、会话、应用大纲、阶段条、确认卡、WorkflowRunCard、Diff、Preview 和验收 Dock。
2. 原型代码不得整体复制到生产目录。每个复用点必须对照生产依赖、Ant Design v4、现有主题 token、严格类型和当前 AG-UI 契约重新实现。
3. 不引入第二个 UI 框架或大依赖；新增生产依赖前单独说明必要性并获得确认。
4. 新增或实质修改的 UI 必须支持亮色和暗色主题，包括背景、文字、边框、hover/focus、overlay、empty/loading/error/success 状态；不得引入偏离当前紫色主题的孤立硬编码色。
5. 桌面端交互以已运行 Electron 应用为验证对象；Vite 页面只能作为开发服务健康信号，不能替代 Electron UI 验证。
6. 每个函数或方法必须有说明用途的中文注释；复杂逻辑补充关键步骤和非显然决策的中文注释。
7. 活跃源码或样式文件接近 350 行且继续混合职责时，先评估按 feature、hook/service、UI section 或 style partial 拆分，避免继续堆叠。

## 8. 构建、测试、审查与验收规则

1. 智能体实现任务必须编译进现有 Build DAG，并由现有 BuildScheduler、任务权限、真实 Diff 和结果协调器执行；不得创建只在 UI 展示的平行“计划”。
2. 用户确认的计划必须是 Build DAG 的直接上游；模型不得在确认后再次发明范围、接口、文件或产品语义。
3. 每个任务必须声明 owner、依赖、允许路径、change scope、完成标准和 required checks。越权写入在工具层拒绝，不能只依赖 Prompt 或事后提醒。
4. 质量结论必须来自真实命令、退出码、测试数量、Diff、运行态和验收证据；Agent 自述、Mock 结果或“无失败文本”不能作为通过依据。
5. 智能体功能复用现有 Unit Testing、Integration Testing、Code Review、Launch 和 Acceptance；只新增智能体专属检查项，不复制整套阶段。
6. 前端变更至少运行 `pnpm build` 和相关测试，并在 Electron 中验证真实流程、控制台、网络、亮/暗主题及关键空/错/加载状态。
7. 后端变更至少运行聚焦语法/导入检查、相关测试和 `curl -sS http://127.0.0.1:8000/health`；涉及协议时增加前后端契约或事件重放测试。
8. 完成前执行多轴代码审查，检查功能、回归、类型、错误处理、并发、恢复、安全、性能、可访问性和文档一致性。
9. 每个验收结果绑定具体 artifact/config revision、代码 Diff、测试报告、启动证据和用户决定；未验证项必须明确展示。

## 9. 安全与权限规则

1. 智能体、工具、知识和外部资源都视为不可信输入；Prompt 约束不是安全边界。
2. 工作区、文件、命令、网络、数据库和凭据权限必须由统一且不可绕过的工具策略执行，按 run/target/参数 hash/TTL/单次消费绑定审批。
3. 不接受任意物理 `workspace_root` 或 artifact 路径作为产品契约；优先使用可信注册的 workspace/artifact ID，并做 canonical containment 与 no-follow 校验。
4. 禁止把 `.env`、token、数据库密码、私钥或完整敏感 Prompt/日志传给模型、前端、生成应用、安装包、会话记录或默认日志。
5. 模型选择、API、实体、知识库和工具授权必须遵循最小权限；子 Agent 只能继承授权子集。
6. 数据库写、破坏性文件操作、依赖安装、网络访问、发布、push 和部署使用独立高风险审批，不得由智能体自行批准。
7. 同一 workspace 的正式写 execution 在没有隔离 worktree/分支与确定性合并门前必须串行；显示锁不等于真实互斥。
8. 模型生成代码的预览或试聊运行时必须与主 Renderer、preload、凭据和宿主文件系统隔离，不能复用不安全的同源执行方式。

## 10. 每批交付与台账

每个已确认批次完成后必须：

1. 更新 [智能体开发流程实现状态](./AGENT_DEVELOPMENT_IMPLEMENTATION_STATUS.md)，记录真实状态和证据。
2. 若目录归属、公开 API、Electron IPC、存储格式、AG-UI payload、工具契约或 feature boundary 变化，同步更新 `docs/CODEBASE_INDEX.md`。
3. 汇报修改文件、复用点、未触碰边界、验证命令、通过/失败/跳过结果和剩余风险。
4. 不自动提交、push、merge、发布或覆盖用户 staged changes；这些操作必须由用户单独授权。

## 11. 必须停止并重新确认的条件

出现以下任一情况，当前批次立即停止写入并请求用户确认：

- 需要改变现有页面/API/实体主流程或默认行为；
- 当前文档/代码与已确认方案冲突，且无法在原范围内确定唯一解；
- 需要确定新的 Artifact DAG、公开 schema、运行时归属、存储格式或兼容策略；
- 需要新增生产依赖、普通 REST 产品接口、第二套状态源或平行 Workflow；
- 需要扩大文件、数据库、网络、凭据、发布或工作区权限；
- 发现用户未说明的历史数据迁移、破坏性操作或不可逆副作用；
- 无法为“不破坏已有功能”建立相称的自动化和 Electron 回归证据。
