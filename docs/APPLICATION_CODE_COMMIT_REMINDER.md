# 应用创建旅程中的代码提交提醒时机与实施方案

## 一、背景

XCodeAgent 在创建应用的过程中会经历许多环节，在不同的阶段会生成和注入不同的代码。目前项目内缺失代码提交的主动提醒，若用户一直到应用全部完成后才进行一次提交，代码历史会出现以下问题：

- 页面、接口、数据库和公共能力的变更混在一起，难以定位来源；
- 生成失败或验收调整后的修复无法清晰区分；
- 用户无法在每个业务模块完成后形成可回滚的稳定版本；
- 应用关闭、切换项目或中断工作流时，未提交修改容易被遗忘。

因此，需要在应用创建旅程中识别“已经形成可追溯版本”的时机，主动提醒用户提交代码；同时也需要避免在代码尚未验证、Agent 仍在写入或仅产生内部规划产物时g频繁打断用户。

## 二、两类应用创建流程与阶段分析

XCodeAgent 的代码生成可以归纳为两类流程：一类是从零开始的新建应用流程，另一类是针对已经完成设计的页面或 API 进行二次修改的流程。两类流程都遵循“执行代码变更 → 验证 → 形成可追溯版本”的原则，但新建流程需要先建立应用基线，二次修改流程则直接围绕已有模块形成增量提交。

### 2.1 正常新建应用流程

```text
需求与项目计划 → 模板初始化 → 页面/API 详细设计 → 构建任务 → 测试与验收 → 项目收尾
```

| 阶段 | 阶段工作与主要产物 | 提醒判断 |
| --- | --- | --- |
| 需求、项目计划与详细设计 | 完成需求澄清、ProjectPlan、页面和 API 详细设计，产出 Markdown/JSON 规划文档，作为后续代码生成的输入。此时主要是产品和工程设计，通常还没有业务代码。 | 不需要代码提交强提醒；如团队希望保留设计版本，可使用弱提醒，并明确文案是“保存设计版本”而不是“提交代码”。 |
| 模板初始化 | 下载前后端模板、生成占位页面和菜单，写入应用基础目录，产物是可以进入工作区的初始工程。当前模板自身的 Git 历史会被移除，因此应用根目录需要建立独立仓库。 | 需要强提醒；建议创建一次应用初始化基线提交，作为后续页面和 API 提交的比较起点。 |
| 构建任务与代码生成 | 根据已确认设计生成 Build DAG，执行数据库、后端和前端任务，产物是实际代码变更、任务结果和可追踪的代码变更集。单个任务完成时，模块可能仍不完整。 | 单个任务完成不主动打断；模块任务基本完成且局部检查通过时可以中等提示，但不应在 Agent 仍写入或存在失败任务时要求提交。 |
| 集成测试、预览与验收 | 执行编译、契约、接口和集成检查，启动预览并等待用户验收，产物是测试报告、预览信息和结构化验收结果。验收通过后，页面/API 才同时具备技术和业务闭环。 | 质量门禁通过、等待验收时中等提示；用户验收通过并完成项目收尾时强提醒，按页面/API/模块形成一次提交。 |

### 2.2 已完成设计页面/API 的二次修改流程

```text
选择已设计页面/API → 识别修改范围 → 执行增量修改 → 测试与预览 → 快速修改收尾
```

| 阶段 | 阶段工作与主要产物 | 提醒判断 |
| --- | --- | --- |
| 修改范围识别与增量执行 | 用户在已有页面或 API 上提出修改，系统识别前端、后端或全栈范围，并在授权路径内写入代码，产物是本轮会话关联的增量代码变更。执行期间仍可能继续追加修改。 | 不提醒；Agent 正在运行时不应启动提交或暂存。 |
| 测试与预览 | 对本轮修改执行相称的测试并启动预览，产物是测试结果、启动结果和当前工作区差异。测试通过说明具备提交条件，但不一定代表用户已经确认业务效果。 | 测试通过、等待用户确认时中等提示；测试失败但有代码变更时提示审阅、继续修复或撤销，不建议直接提交。 |
| 快速修改成功收尾 | 用户确认修改结果后，快速流程结束并保留会话、页面/API 归属和代码变更信息，产物是一个相对独立的增量修改单元。 | 需要强提醒；建议直接生成小范围 `fix` 或 `feat` 提交，避免与下一轮修改混在一起。 |

### 2.3 两类流程共同适用的离开场景

离开提醒是防止遗漏的兜底机制，不是主要提交节点。切换页面/API 时只显示未提交角标或一次性 Toast；返回欢迎页、切换应用时，如果存在已验证但未提交的修改，可以给出中等提示；显式退出应用时再升级为强提醒。普通关闭窗口如果只是隐藏到托盘，则不阻断用户，但应保留待提交状态。

无论哪类流程，Agent 正在写入代码、工作流仍有可执行任务或提交前工作区指纹已经变化时，都不应直接提交；应等待执行结束并重新审阅实际 Git 状态。

## 三、提醒策略结论

从整个应用创建过程看，提交提醒不应平均分布在每个节点，而应围绕“代码边界”和“验证结果”分层：

- **正常新建流程**：模板初始化完成时建立一次强提醒基线；构建任务阶段以弱提醒或候选检查点为主；质量门禁通过时给中等提示；用户验收通过并完成收尾时给强提醒，形成页面/API/模块级提交。
- **页面/API 二次修改流程**：执行期间不提醒；测试通过后给中等提示；用户确认修改并成功收尾后给强提醒，形成独立增量提交；失败或停止但留下代码时只提示审阅、修复或撤销。
- **两个流程共同的离开机制**：页面/API 切换使用弱提醒，切应用或返回首页使用中等提示，显式退出使用强提醒。提醒应根据工作区、模块和 dirty fingerprint 去重，避免同一批代码反复打扰。

“设计确认”和“代码提交”需要保持概念分离；“暂存”可以作为提交审阅过程中的内部步骤，但不应替代提交本身。真正用于追溯的结果应是用户确认后的 Git commit，默认不自动 push、stash、amend 或覆盖用户已有的暂存内容。

## 四、具体实施方案

### 4.1 强提醒

强提醒用于已经形成稳定、可追溯版本的节点。原则是：有明确业务边界、没有正在写入的 Agent、且代码已经通过相应验证。

| 提醒时机 | 提醒强度 | 推荐的实现方式 |
| --- | --- | --- |
| 模板下载、占位页面和基础菜单生成完成，首次进入工作台 | 强提醒 | 提示创建应用根目录 Git 仓库并完成初始化提交；提交前生成根 `.gitignore`，排除 checkpoint、缓存、日志、凭据和提醒状态；禁止误用父目录仓库。 |
| 页面/API 代码生成完成，集成测试和质量门禁通过，用户预览验收通过 | 强提醒 | 在验收完成卡片后直接展示“提交本次模块代码”；默认按页面、API、数据库依赖和本轮 `runId` 聚合变更，展示文件清单、测试结果和建议提交信息。 |
| 验收调整后的修复已重新通过测试并再次验收 | 强提醒 | 将修复作为新的 commit 提交，不自动 amend 原提交；提交信息中明确使用 `fix` 或“验收修复”语义。 |
| 快速修改流程成功完成 | 强提醒 | 快速修改收尾后展示一次小范围提交建议；关联当前页面/API 会话和实际文件差异，不要求重新生成正式 ProjectPlan。 |
| 用户准备显式退出 XCodeAgent，且存在已完成但未提交的代码变更 | 强提醒 | 在退出前显示审阅确认；提供“审阅并提交”“仍然退出”“取消退出”，退出确认前重新读取 Git 状态，避免提交过期差异。 |

### 4.2 中等提示

中等提示用于代码已经接近稳定，但还没有完成完整业务验收，或者用户正在离开一个较大的工作上下文。

| 提醒时机 | 提醒强度 | 推荐的实现方式 |
| --- | --- | --- |
| 集成测试和质量门禁通过，项目已启动并等待用户验收 | 中等提示 | 在预览区或 Workflow 结果卡中显示“代码已通过自动检查，可先创建版本”；不阻断预览和验收，用户验收后升级为强提醒。 |
| 一个页面或 API 的全部构建任务完成，且局部检查通过，但整个执行仍未结束 | 中等提示 | 记录候选提交点并显示角标，不立即弹窗；若用户主动打开版本面板，可按模块查看候选文件。 |
| 用户返回欢迎页或切换到另一个应用 | 中等提示 | 仅当当前应用存在已验证、未提交的修改时弹出确认；如果 Agent 仍在运行，提示继续执行或稍后处理，不启动提交。 |
| 当前应用的执行失败或被停止，但已经产生代码变更 | 中等提示 | 显示“存在未完成修改，请审阅、继续修复或撤销”；默认主操作应是审阅，不应把失败代码直接包装成可提交版本。 |
| 应用全部页面/API 已完成，但仍存在零散未提交文件 | 中等提示 | 在项目完成页提供“检查遗漏变更”入口，列出未关联到任何模块的文件，要求用户确认归属后再提交。 |

### 4.3 弱提醒

弱提醒用于频率较高、通常不应打断用户的场景，主要承担可见性和防遗忘作用。

| 提醒时机 | 提醒强度 | 推荐的实现方式 |
| --- | --- | --- |
| 页面或 API 之间切换 | 弱提醒 | 在工作区名称、页面条目或版本控制入口显示未提交数量角标；必要时使用一次性 Toast，不使用每次切换都弹出的模态框。 |
| 设计文档确认完成，但尚未生成业务代码 | 弱提醒 | 使用“设计版本已确认”或“可保存设计文档”文案，与代码提交入口分开；默认不触发代码提交弹窗。 |
| 单个 Build task 完成 | 弱提醒 | 仅更新任务卡中的“可形成检查点”状态，不主动打断当前任务批次；待模块测试或验收完成后统一处理。 |
| 普通关闭窗口并保持托盘运行 | 弱提醒 | 不阻止隐藏窗口；在托盘菜单或重新打开工作台时保留未提交角标和提醒状态。 |
| 用户选择“稍后提交” | 弱提醒 | 按工作区、模块和 dirty fingerprint 去重；代码未发生新变化时不重复弹出，显式退出或最终项目完成时可再次提醒。 |

## 五、实施边界与安全要求

### 5.1 Git 状态以工作区事实为准

现有 Workflow 已能产生 `codeChanges`，但提交前仍应重新读取 Git status 和 diff。代码变更集用于解释“谁改了什么”，Git 状态用于确定“当前实际有什么”。两者不一致时，应提示用户重新审阅。

### 5.2 提交必须经过用户明确确认

建议采用“审阅 → 选择文件 → 编辑提交信息 → 预检 → commit → 再次读取 status”的流程：

1. 展示本轮修改文件、增删统计和关联模块；
2. 默认只选择本轮授权范围内的文件；
3. 检查敏感文件、越权路径和已有暂存修改；
4. 执行 `git diff --cached --check` 等确定性预检；
5. 用户明确确认后再执行 commit；
6. 提交完成后验证 HEAD 和剩余未提交文件。

不建议使用 `git add .`，也不应静默合并用户在外部 IDE 中已经暂存的内容。

### 5.3 提醒去重与并发校验

每次提醒应带有工作区和变更指纹，例如：

```text
workspaceRoot + HEAD + staged status + unstaged status + untracked list
```

提交前如果指纹发生变化，应重新生成审阅内容。提醒状态可以保存为工作区内部的版本控制状态，但该状态文件本身必须被 `.gitignore` 排除，不能因为提醒状态变化而制造新的业务代码变更。

### 5.4 AG-UI 和现有工作流的关系

后续实现应新增独立的版本控制 AG-UI 动作流，例如 `version-control/run`，承载状态检查、提交准备、提交和稍后提醒等产品动作。它不应把 Git commit 逻辑塞进模型 Prompt，也不应让 Workflow 节点自动提交。

主 Workflow 只负责产生里程碑信号，例如模板生成完成、质量门禁通过、验收完成和快速修改完成；版本控制服务负责读取实际 Git 状态并向用户提供提交动作。这样可以保持工作流、代码生成和 Git 操作之间的职责边界。

## 六、预期效果

实施后，用户可以获得以下清晰的版本历史：

```text
应用初始化基线
→ 页面/API 模块提交
→ 验收修复提交
→ 快速修改提交
→ 应用最终收尾提交
```

每个 commit 都尽量对应一个已验证的业务单元，失败任务和半成品修改仍然保留在工作区中供继续修复或撤销，不会被误包装成稳定版本。这样既能避免所有代码最后一次性提交，也能避免提醒过于频繁而干扰应用生成流程。
