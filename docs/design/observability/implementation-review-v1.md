本次已修正计算文档的页面/API口径、首版本样本、首次评价分类、实时性说明，以及 Schema 的 Token 完整性条件。**未增加新的上传字段或事件**；仍需完善的业务样本、源版本关联尚未进入当前 Schema；开发对应质量归因能力前需要先补合同。本期不新增实时阶段或代码入库算法字段。

## 1. 仍需处理的技术问题（开发负责）

| 优先级 | 问题与影响 | 开发处理方式 / 当前状态 |
| --- | --- | --- |
| P1 | 应用身份没有在所有入口保持稳定。重新添加无索引的工作区会新生成 ID；普通 workflow 的 project_id 可被覆盖，conversation metadata 中缺少 project_id。可能把同一应用拆成多个身份、触发既有所有权校验冲突，或让 Token/耗时无法归属。 | 在业务权威身份层明确应用身份，重开/重新添加按约定复用身份；所有前台、恢复、后台 Worker 继承同一个应用与发起者身份。不能用路径、分支名或当前选中的应用反推。**尚未实现。** |
| P1 | `(operation_id,stage,node)` 不是所有业务结果的唯一样本键。同一页面可并行多个 Unit；同节点可多次生成候选。把它们折叠到最新结果会丢失败，repair/测试累计快照相加又会重复。 | 冻结“一次独立业务生成/测试过程”的稳定样本身份，例如业务样本 ID 或明确的 Unit/候选身份；定义自动修复链及用户 Retry 关系、结果顺序。为同一结果指定唯一生产边界，不同时数 Model/Node/Workflow 的重复摘要。**当前字段和关联规则尚不完整。** |
| P1 | 模型正常返回不等于业务校验通过。很多真实成功/失败、首轮通过、修复结局、测试/启动结果并不会自动成为 LangSmith 的结构化 result。若结果依旧按需遗漏，质量报表可能没有分母。 | 按业务阶段列出必采结果字段和触发边界。真实业务结果写到完成校验的 Node/操作边界；不从 Model 技术 status 推断，也不回写已经落盘的不可变模型 Span。**需要具体采集规范。** |
| P1（严格修订/返工归因） | 新生成候选过程可能换 operation_id，但没有源文档版本/源操作关联。能统计用户修改请求，却不能精确证明哪个旧文档实际被重生成、模板是否减少跨操作返工。 | 为相关修订/再生成事实建立明确源产物版本或源操作关联，并定义实际生成成功边界。当前报表只能先报已采集的评价不通过率、revision 成本或同一操作内修复情况。**不能把代理指标换名字当精确指标。** |
| P2 | 前版 Schema 接受 usage_status=complete 但三个 Token 都是 null。只跑结构校验会把脏数据当完整统计。总 Token 算术、时间前后、区间范围等仍不由一般 JSON Schema 自动保证。 | 已增加 complete/partial/unavailable 与数值可空性的条件约束。接收端必须再验证 total=input+output、时间/区间边界、身份授权和版本快照绑定；启用真实日期格式检查，而不是只检查字符串正则。 |
| P2 | 过滤 LangChain chain 包装后，直接复制 parent_run_id 可能让 model/tool 指向一个永远不上传的父 Span，链路图断开。 | 规范化时重连最近保留祖先，并统一选定根的 trace_id；包装不是业务节点。需要父先后乱序到达的暂存/关联处理，不把合法跨批次父节点当作丢失。合同说明已修正，采集器尚需实现。 |
| P2 | “失败整批重试”未区分网络故障和永久坏记录；一个非法记录可能阻塞整个持久队列。源字段缺失、错误 ACK 或落盘失败也不能宣称零丢失。 | 定义成功 ACK、按 record_id 定位的永久错误隔离、临时错误退避、413 拆批。ACK 只能在可靠持久化后给出；同 ID 不同内容应报冲突而不是静默丢弃。网络/进程恢复只对已成功落盘记录保证重试，落盘失败要有可观测诊断且不干预业务。 |

## 2. 已修正或明确的计算口径

- 页面/API数：用户确认主报表为截至统计时点累计完成过的数量，含未发布应用；同一产物只计一次，删除/返工不扣减。周期新增另按首次完成时间计算，当前存量快照不在本期范围。
- 首版本均值：仅完整观测的新应用参加。创建事实缺失、已有/导入应用或首次观测发布不是首发的样本不能伪造创建时间或首版本；完整时间/Token联合均值用共同有效样本集合。
- 有效使用时间：按统计对象合并根执行区间，扣除用户等待。后台 Worker 也要采到实际区间并继承原身份；模型/工具等待属于调用运行过程。UTC 用于对齐、单调时钟用于时长；跨进程/机器时间对齐需验证。
- 首次评价：区分原稿接受、编辑后接受、要求 AI 修改、重生成和跳过，取候选首次有效评价；最终采纳另报，不用后续 accept 覆盖原稿首次不满意。
- QPS/并发：用户确认使用事后报表；现有结束记录可支持历史逻辑调用 QPS 与历史并发回放，允许迟到回补，不再把实时开始采集列为本期阻塞项。Provider物理请求和隐藏 SDK 重试仍不属于统计承诺。
- 代码入库：用户确认已有计算方式，本方案不再讨论或规定本地/远端入库条件、归因和聚合方式，只承接其已有结果。
- 输出 TPS：当前公式是客户端观察首尾输出区间的估算速率。若 output_tokens 含不可见 reasoning 或输出分块缓冲，该公式不代表服务端真实 Token 生成速度。
- 覆盖率：已观测 Trace 中字段可用比例不等于所有真实调用的零丢失比例。后台调用、异常前后、关闭/切换应用等采集路径必须实测。

## 3. 开发前的最小验收案例

| 场景 | 必须得到的结果 |
| --- | --- |
| 同一应用重开、重新添加工作区、切换分支；A 应用运行时切到 B | 按业务身份约定稳定归属；后台 Trace 不误记到 B。conversation/恢复/Worker 入口不得无故缺应用身份 |
| 根执行 0–10 秒、并行 Worker 5–15 秒，用户等待 15–45 秒，再执行 45–50 秒 | 累计有效时间为 20 秒；不相加父子、不计 30 秒用户等待；分周期时截断区间 |
| 同页面同节点并行两个 Unit，一个成功一个失败 | 两个独立业务样本，不折叠为一个成功，也不把它们当两次页面启动 |
| 首轮失败→自动修复失败→用户 Retry 成功 | 首轮失败、自动修复失败、业务最终成功三种事实都准确；不是自动修复成功 |
| 只完成页面/API、尚未发布；重复完成同一目标，之后删除目标 | 累计完成量首次加一，重复完成及删除不改变累计值，不要求当前存量快照 |
| 先入队 A、B；同一事件重复上传；结束记录晚到；父 Span 跨批次到达 | 幂等不重复、按事实时间归属周期、合法父子能关联；同 ID 内容冲突可定位 |
| Token 全缺失/部分已知/完整；complete 但 null；total 不等于 input+output | 前三种正确分类；后两种不能进入完整统计。Schema拒绝可表达的非法状态，算术错误由语义校验拒绝 |
| 模型结束后上报，跨统计窗口或迟到；单块/非流式输出；SDK隐藏重试 | 事后 QPS 按真实开始时间归属并回补；TTFT/TPS不可得时为空；不把逻辑调用率说成 Provider物理 QPS |
| 同一个版本 HEAD 重复成功推送 | 不新增版本，不改变版本首次成功时间；代码入库计算仍由用户已有算法负责 |
| 首发早于当前周期但事件晚到；采集上线前已有应用后来发布 | 归属真实首发周期并允许回补历史报表；已有应用的首个观测发布不冒充真实首版本，不迁移旧合同或伪造旧数据 |
| 产物编辑后确认；先不满意，之后采纳 | 原稿接受率不虚高；首次评价与最终采纳分别计算 |
| schema 错误/跨字段错误、网络超时、服务 5xx、413、落盘失败 | 永久坏数据不会无限阻塞有效记录；临时错误重试、超大批次拆分；不因观测失败改变 Workflow |
