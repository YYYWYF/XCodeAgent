# 智能体接入现有 Prototype 的交互规格

## 目标与依据

本规格只描述 `prototype/` 中新增的智能体开发与页面集成流程。交互事实以当前 prototype 的页面、接口开发流程为准，并遵循现行 `docs/WORKFLOW.md`、`docs/APPLICATION_LIFECYCLE.md`、`docs/MODEL_OUTPUT_COMMUNICATION_DESIGN.md` 与 `docs/PROCESS_STREAMING_DESIGN.md` 的门禁、状态和过程展示原则。

`docs/AGENT_DEVELOPMENT_REQUIREMENTS.md` 与 `docs/AGENT_PRODUCT_FLOW_REVIEW.md` 属于已废弃方案，不作为本规格的输入，也不修改它们。

## 产品定位

- 智能体是应用版本中的开发产物，与页面、接口、模型同级，不新增顶层工作台或管理后台。
- 产物树顺序为：页面、智能体、接口、模型；智能体与页面、接口、模型处于同一级。
- 智能体状态沿用统一状态机：未开始 → 进行中 → 已完成。
- 一个智能体只能由默认对话持有编辑权；其他对话只能读取或明确申请加入。
- 已发布版本锁与现有页面、接口保持一致；当前未发布版本允许从测试或审查阶段的智能体配置面板发起增量修订，提交后回到该智能体的开发工作流。
- 智能体依赖使用稳定引用：`modelId` 标识模型，`apiReferences` 同时携带 `apiContractId`、`endpointId`、路径和实体引用，`knowledgeReferences` 标识已确认知识；展示名称不能替代这些引用。
- 智能体声明的实体依赖必须先通过当前版本的实体详细设计确认；已发布版本的完成态不能泄漏到新迭代。

## 参考架构映射

- `learn-coding-agent`：交互过程保留“收集上下文 → 调用工具/API → 校验证据 → 继续或结束”的小循环；prototype 只模拟该循环的可见事件，不伪装成真实运行时。
- OpenCode：沿用规划/构建边界、工具权限和可恢复会话思路；智能体详细设计先只读审阅，确认后才进入构建态。
- Deep Agents：正式实现继续采用规划、文件系统产物、子智能体、上下文压缩、长期状态和人工介入的 harness 形态；本次不在 prototype 内另造运行时。
- 128k 上下文预算：每轮只注入当前页面、已确认设计、必要工具结果和压缩后的过程摘要；完整仓库、无界历史和大段日志存入工作区，只向会话返回引用和摘要。
- XCodeAgent 的刻意差异：智能体不是独立顶层产品或新的运行入口，而是应用版本中的可开发产物，并通过已有 AG-UI 工作流进入页面构建和预览。

## 完整交互流程

### 1. 创建开发对话

1. 用户在开发阶段首次进入工作台，或点击灰色的未开始智能体。
2. 系统在现有“从一个产物开始开发”树中展示智能体，与页面、接口使用同一选择与确认弹窗。
3. 用户确认后才创建默认对话、AG-UI thread，并把智能体推进到“进行中”。
4. 取消操作不得创建会话、取得写锁或改变产物状态。

### 2. 智能体详细设计

1. 对话区展示与接口一致的“待设计”挡板卡，说明智能体用途、模型、工具/API 依赖和目标页面。
2. 在进入智能体设计前，工作流执行 `inspect_agent_dependencies`，按稳定 ID 检查 `modelId`、API/端点、实体和知识引用。
3. 如果实体未完成详细设计，显示“智能体依赖门禁”：用户可以进入实体设计、确认实体 Markdown，或重新检测；实体确认只对当前应用版本生效，未完成门禁不能生成 Agent 设计。
4. 所有依赖完成后，点击“开始详细设计”通过现有 AG-UI 会话发送智能体目标身份。
5. AG-UI 返回正式 Markdown 设计产物的审阅卡，固定按以下十个部分组织：任务、规则、限制、输入、输出、模型、对话体验、记忆、工具、知识检索。
6. 用户明确确认该版设计后，才允许进入任务规划与构建；补充信息不等同于确认，修改后的新版本需要重新确认。

### 3. 构建、验证与预览

确认后沿用接口的流内过程卡，按顺序展示：

1. 检查工作区与已有产物。
2. 校验模型、工具/API、实体和知识依赖。
3. 规划构建任务 DAG。
4. 使用 Python 生成智能体定义和工具适配器，并生成必要的页面接入代码。
5. 按文件逐个展示真实目标路径的 Diff；每个文件都必须由用户接受后才进入下一个 DAG 任务。
6. 所有文件接受后，依次执行 `integration_test`、`launch_project` 和 `acceptance`，没有验收确认不得把智能体标记为已完成。

构建目标固定为三类文件：

- Python 智能体定义：`agent-runtime/agents/<agent>.py`。
- Python 工具适配器：`agent-runtime/tools/<agent>_tools.py`。
- 页面侧接入：`frontend/src/pages/<pageId>/components/<Agent>.tsx`。

每次只提交一个文件的 `codeChanges`，Diff 中显示新增/删除行、来源工具、目标路径和接受状态；接受后保存到当前应用工作区，DAG 同步显示已完成、运行中和待执行任务。

右侧工作区沿用现有 tab 交互，提供：

- 智能体文档：用户确认的 Markdown 设计。
- 实现源码：Python 智能体定义与工具绑定代码。
- 试运行：采用与现有对话一致的消息流。用户发送消息后立即追加用户消息，生成完成后追加智能体回复；支持连续多轮追问并保留本次会话上下文。工具调用摘要、证据和错误状态作为回复详情展示，不展示隐藏思维链。
- 预览验收：启动后的页面预览必须能发送消息并得到回复，显示工具证据；失败场景显示错误和重试入口，验收卡要求用户确认正常回复、连续追问、权限拒绝和失败重试。
- 过程：复用现有 Workflow/ProcessSteps 过程记录。

### 3.1 配置面板修改与增量重新生成

右侧智能体配置面板与页面、接口的开发入口保持同级，但配置修改不直接覆盖当前生效产物。配置状态按 `versionViewKey + agentId` 隔离，并在当前智能体会话内分为三份：

- 生效配置：当前左侧对话、文档、源码和试运行实际使用的版本。
- 编辑草稿：用户在人设与回复逻辑、模型、技能、知识检索、工具、对话体验六个模块中修改的内容，切换右侧 tab 时仍保留。
- 候选配置：点击“应用配置并重新生成”后冻结的版本，等待左侧确认卡和后续代码验收。

配置修改通过现有 AG-UI 工作流提交，流程为：

1. 用户在右侧编辑配置并点击“应用配置并重新生成”；未发生变化时不创建新的运行。
2. 左侧追加“智能体配置变更”确认卡，列出变更模块和候选模型。此时当前生效代码、左侧对话和试运行保持不变。
3. 用户取消时丢弃候选配置；用户确认后进入现有 `inspect_workspace`、依赖校验、任务 DAG 和逐文件 Diff 流程。
4. 配置候选会同步到十段式 Markdown 设计、Python 智能体定义和 Python 工具适配器；页面接入文件仍复用同一次 Agent 构建任务，避免配置变化绕过页面集成链路。
5. 每个文件 Diff 仍需单独接受；全部接受后继续 `integration_test` → `launch_project` → 智能体验收。
6. 只有用户确认智能体验收后，候选配置才提升为生效配置，左侧对话和试运行才切换到新模型、资源和对话体验设置。生成失败、取消或未完成验收都保留旧生效版本。

配置工作流的 `agent_config_review` 只负责候选版本确认，不替代正式设计和文件 Diff 门禁；候选配置通过 AG-UI 的 state/result 快照在恢复时传递，前端不另建 REST 或手写流式协议。

### 4. 集成到页面

- 页面详细设计可以选择项目计划中已声明、且已完成详细设计的智能体作为依赖。
- 智能体集成信息进入页面现有详细设计文档和构建 DAG，不创建独立“页面绑定”后台。
- 页面与智能体由同一开发任务负责时，可以显式归入同一个默认对话，并分别取得产物写锁。
- 页面预览在原页面内展示智能体入口、对话状态、加载、空态、失败与人工接管状态。
- 页面验收同时验证页面 → 智能体 → API/工具的调用链和权限边界。
- 页面与智能体的消费关系写入页面详细设计和构建任务，智能体实现不绕过页面现有的会话、权限和预览入口。

### 5. 版本、会话与验收状态

- 页面、接口、实体和智能体的“已设计”标记按 `versionId` 隔离；新迭代或回滚后的迭代重新进入对应门禁，不复用其他版本的内存状态。
- 会话身份至少包含 `agent:<agentId>`，实体设计会话使用实体稳定 ID；恢复时同时校验 thread、run、目标产物和生命周期 pending interaction。
- 智能体只有在所有文件 Diff 被接受、集成测试和预览启动完成，并且用户提交 `agent_acceptance=accepted` 后，才写入当前版本的完成态。
- 版本在完成设计后仍属于 `iterating`，设计、开发和测试前的调整不会触发版本只读；只有用户在审查完成后确认“生成版本”，状态才变为 `released` 并锁定。
- 当前版本处于 `iterating` 时，智能体配置不受“正在查看较早开发阶段”限制；用户可以继续修改草稿并通过配置确认、代码 Diff、集成测试和验收生成新的候选实现。已发布版本和历史版本仍只读。
- 测试报告、代码审查和最终交付沿用应用级共享流程；Agent 作为测试范围和审查报告中的一个明确模块出现，不创建独立顶层阶段。

## Prototype 演示场景

武汉分行需求回检系统新增智能体“回检填报助手”：

- 目标页面：我的回检。
- 模型：项目默认模型。
- 工具/API：`GET /api/rechecks/my`。
- 能力：解释回检状态、根据当前用户的回检单给出下一步操作建议。
- 权限：只读当前用户可见数据，不允许代替用户提交或修改回检单。
- 页面集成：在“我的回检”页面右侧提供助手入口，试运行与页面预览均展示工具调用证据。

## 验收标准

- 产物树、筛选、首次开发选择和确认弹窗中都能看到智能体。
- 未确认创建前不产生会话或状态变化；创建后默认对话和锁行为与接口一致。
- 智能体详细设计必须人工确认后才能构建。
- 智能体实体依赖未确认时必须停在 `inspect_agent_dependencies`，不能直接生成详细设计或构建代码。
- 构建过程使用现有 AG-UI 消息、Workflow 卡和 ProcessSteps，不引入手写 SSE/REST 产品流。
- 右侧可查看智能体文档、源码和试运行；浅色、深色主题均可读。
- 智能体文档严格包含任务、规则、限制、输入、输出、模型、对话体验、记忆、工具、知识检索十个部分，智能体源码以 Python 展示。
- 智能体构建至少产生 Python 定义、Python 工具适配器和页面接入三个目标，并按真实文件逐个 Diff 接受。
- 所有文件接受后必须经过 `integration_test`、`launch_project` 和用户驱动的 `agent_acceptance`；未验收不得把 Agent 状态写为已完成。
- 试运行必须通过发送消息获得智能体回复，并保留连续多轮消息；不得用固定结果卡代替对话。
- 失败请求必须显示错误状态和重试入口，回复必须带有当前用户数据范围和工具证据。
- “我的回检”页面详细设计和预览能体现对“回检填报助手”的消费关系。
- 已发布版本只读，历史对话可重放，新迭代和回滚后的版本不会继承错误的设计完成标记。
