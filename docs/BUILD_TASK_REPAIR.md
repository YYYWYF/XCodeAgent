# Build 单任务计划修复

当前实现提供“修复任务”：AI 根据当前失败和真实源码生成一个任务的文件计划草稿，用户审阅并明确确认后，平台执行修复后的任务。原“重试任务”保持合同不变，两者独立。

## 操作入口

失败的正式 frontend/backend Agent 任务，在最新 Build 消息的任务详情底部提供入口。明确归因到一个正式任务的 DAG 校验阻断也可进入。Build 必须已经停止派发且在途执行已收口；数据库审批、其他正式确认、已结束任务、旧会话卡片及平台确定性任务不可进入。

前端 `buildTaskRepairEligibility.ts` 对模型错误、网络错误、超时及无效结构化响应隐藏修复按钮；同时从失败原因和诊断中识别 ModelTransmitError 等模型调用异常，覆盖其被包装为 runner_crash 的情况。这是按钮展示规则，后端准入不增加对应限制，原任务重试入口保持既有规则。

点击“修复任务”立即根据服务端报错和相关源码自动诊断、生成草稿，无前置弹窗或补充要求输入；同一任务已有待确认草稿时直接展示。生成中在任务卡右下方显示加载提示，失败原因用红字显示。确认区默认仅展示根因、增量修复步骤以及本次发生变化的文件权限/要求，不重复展示完整任务。原任务与修复后完整内容、业务验收要求收起在“查看完整任务”中。

用户可以先收起任务详情，稍后展开继续审阅；“放弃修复”消费当前草稿，原任务与源码不变；“重新生成”仍依据报错自动诊断，先作废旧稿，失败也不能继续确认旧稿。“确认并执行”绑定用户看到的草稿摘要，切换到原 Build 卡片显示执行进度。生成方案本身不会执行代码，必须经过用户明确确认。

## 单任务边界

任务身份、标题、Unit、owner、阶段、接口身份、依赖和原交付职责由平台保留。模型只提交 `repairInstructions` 增量修复说明，以及需要补充权限、修正操作或追加修复要求的 `files`；禁止提交标题或完整任务说明。只需补充说明时 files 可为空。平台保留原说明并追加修复步骤，原文件未出现在增量中时完整保留；已有文件只追加修复要求并按需调整操作，原交付物路径只增不减。平台将增量合并后派生 target_files、allowed_paths、change_scope 和文件锁，再编译工程及业务检查；不得降低正式业务预期或改动其他任务业务合同。文件重叠引起的并发投影由平台统一重算。

例如仅 ProductPO 缺字段且缺少修改权限时，模型只需提交 ProductPO 的 modify 增量和补字段步骤，不应改写 DTO、Service、Repository 等原计划。确认区默认只显示该 PO 的权限补充，原任务完整文件清单按需展开。执行对象仍是修复后的原任务，增量预览不是代码差异或单文件执行模式。

允许一个 business 任务在原接口职责内修改 foundation 创建的同模块 PO、Mapper 或 Repository。例如正式表结构已有列但 PO 缺字段，草稿可以补充该 PO 的 modify 权限。创建文件的任务不拥有永久独占修改权。原创建任务保持完成，不重跑其代码生成，也不额外复验已完成的共享文件使用方。独立的后端阶段结构检查入口已移除；通用业务自检仍由 `DEVAGENTSTUDIO_DAG_BUSINESS_SELF_CHECK_ENABLED` 控制，默认关闭。执行前任务计划门禁和后续集成检查保持原流程。

本入口只允许当前 owner 的 src 内精确源码路径和 add/modify 操作，不修改表结构、应用配置、模板公共代码、其他 Unit 的已声明文件或正式设计。需同步修改其他任务或业务契约时，AI 应返回阻断原因。完整 DAG 仍有其他错误时，本次草稿不能提升或执行，不能自动扩大当前修复范围。

## AG-UI 合同

端点：`/build-task-repair/run`；请求位于 `forwardedProps.buildTaskRepair`：

| 字段 | 约束 |
| --- | --- |
| action | get / generate / regenerate / discard / confirm |
| workspaceRoot | 当前工作区 |
| sourceRunId、sourceThreadId、sessionId | 当前 Build 的服务端归属 |
| taskId | 唯一正式任务 ID，无批量选项 |
| feedback | 仅 generate/regenerate 接受，最多 4000 字 |
| draftDigest | confirm/discard/regenerate 必须提供，其他动作禁止提供 |

顶层 runId 由前端生成。confirm 的顶层 threadId 必须与原 Build thread 一致；客户端不能提交任务正文、权限清单或执行状态。非执行动作使用 `build-task-repair` 自定义事件及 `buildTaskRepair` 状态快照；包括业务失败在内均提供完整 AG-UI 生命周期。确认后的执行复用标准 Workflow 流，断线读取继续使用标准 Workflow 地址。

## 存储与执行

草稿位于 `.devagentstudio/drafts/task-repairs/<sourceRunId+taskId摘要>.json`，绑定原计划摘要、原执行身份、完整提案及所有诊断文件的内容摘要和存在性。模型无写入工具，最多两次调用；首次可请求一次精确补读，平台限制最多 80 个文件、源码合计 1 MiB，定向目录清单最多 200 个文件名。

确认时再次检查源码、正式输入及计划，拒绝过期和重复消费。平台使用原任务计划锁及 lifecycle CAS/租约交接；新正式计划增加 `task_repair_confirmation`，记录来源 Run、新 Run、任务、会话、草稿摘要和原计划摘要。原 Build Run 的快照与执行记录不改写。新 Run 在代码执行前写入不可变计划及 prepared 进度；仅目标任务转为 pending，其他成功和失败状态保留。

若交接尚未启动即失败，按新计划摘要回退本次提升及 lifecycle，保留可重新确认的原草稿，不覆盖后来提交的新计划。相关源码或计划变化后，旧草稿必须重新生成。

## 手动验收

本次按用户要求不运行自动测试、构建、Python 编译或 Electron 功能验证。新增后端回归文件 `Backend/tests/test_build_task_repair.py`，尚未执行。开发开始时健康检查 `curl.exe -sS http://127.0.0.1:8000/health` 连接失败；用户撤销自动验证要求后未继续启动服务或重试健康检查。

1. 令 business 任务因缺少 PO 文件权限失败；点击“修复任务”后应立即显示自动分析状态，无弹窗或输入要求；方案在原任务卡内出现。核对 PO 为 modify、原接口/依赖不变，确认前磁盘源码无改动。
2. 确认执行，核对只有该业务任务重新执行；PO 原字段和既有方法保留，原骨架任务不重跑，不额外复验已完成的共享使用方。
3. 骨架漏 Repository/RepositoryImpl 时，核对只补充原骨架任务，不添加业务方法或独立业务任务。
4. 收起任务详情后重新展开，草稿仍在；重启 Electron 后重新进入原失败会话，点击“修复任务”应直接恢复待确认草稿。
5. 分别修改源码、正式输入或任务计划后确认旧稿，应被拒绝；重新生成后需要确认新方案。
6. 重新生成失败、放弃修复、重复点击确认、尝试控制历史会话，均不应造成重复执行或改写其他任务。
7. 确认任务完成后不再调用独立后端阶段检查；通用业务自检仍按既有开关执行，后续集成检查保持原流程。
8. 同时存在多个失败任务时，只选择并修复一项；其他成功任务不重跑，其他失败任务不被隐式重试。
9. 对浅色、深色和窄窗口检查原卡片内的文本、文件路径、按钮、焦点、加载/失败提示及方案排版。
