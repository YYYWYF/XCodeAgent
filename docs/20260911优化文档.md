# 20260911 优化文档

记录日期：2026-09-11

## 1. 待优化事项

### OPT-20260911-001：Agent System Prompt 正式配置逐字落地

当前 Agent Runtime 代码生成会读取正式 Agent Contract 中的 `agentSettings.prompt.systemPrompt`，但生成模型可能把该字段当作语义要求进行润色、概括、扩写或删减，导致生成代码中的 System Prompt 与用户确认内容不完全一致。

本问题属于正式配置一致性缺陷。`systemPrompt` 应当被视为用户确认后的不可改写配置，而不是允许代码生成 Agent 自由表达的需求描述。

## 2. 已发现现象

用户确认的 System Prompt：

```text
面向员工的公司政策咨询与请假调休办理助手，用对话方式解答政策问题并引导员工完成请假调休申请与查询。
```

生成代码中的内容：

```python
system_prompt = (
    "作为面向员工的对话式人事智能助手，帮助员工用自然语言完成请假调休申请的梳理与提交，"
    "并解答请假调休等公司人事政策问题。"
)
```

两者语义接近，但生成结果已经发生实质变化：

- “公司政策咨询”被缩小为“人事政策问题”；
- “申请与查询”中的“查询”丢失；
- 增加了原文没有的“梳理与提交”；
- 用户确认的正式 Prompt 没有被逐字保留。

## 3. 当前原因判断

### 3.1 前期契约约束不够明确

当前生成规则要求 CodeRunner 保持 Prompt 内容，但没有把 `systemPrompt` 明确定义为必须逐字复制的不可改写字段，也没有明确禁止润色、总结、同义改写、扩写和删减。

### 3.2 仍由生成模型负责写入正式配置

即使 CodeRunner 能读取完整 Agent Contract，只要正式 Prompt 仍由模型写入源码，就存在非确定性改写风险。仅加强提示词可以降低概率，但不能形成可靠保证。

### 3.3 生成后验收没有比较实际 Prompt

当前 Agent 模块验收主要确认 Agent、模块、Contract Hash、模板 Commit、路径策略和文件修改范围。Contract Hash 能证明任务绑定了哪个正式契约，但不能证明生成代码中的 Prompt 与该契约一致。

因此，即使生成文件存在且修改范围合法，内容被改写后仍可能通过验收。

## 4. 优化目标

正式确认后的 `agentSettings.prompt.systemPrompt` 必须原样进入生成应用。除 JSON/Python 字符串转义及源码换行拼接外，运行时得到的字符串必须与正式 Contract 中的 Unicode 字符串完全相等。

平台安全前缀可以继续存在，但必须与用户 Prompt 分开管理：

```text
最终 Runtime System Prompt
  = 平台锁定安全前缀
  + 用户确认的 systemPrompt 原文
```

平台不得以安全前缀、代码格式化或模板适配为理由改写用户 Prompt。

## 5. 建议优化方案

### 5.1 在正式契约阶段声明逐字保留规则

在 ProductPlan/TechnicalPlan 的 Prompt 契约和校验规则中明确：

```text
agentSettings.prompt.systemPrompt 是用户确认的正式运行配置。
下游节点必须逐字保留，不得润色、概括、同义改写、扩写、删减或重新生成。
```

用户修改并重新确认 Prompt 后，应以最新确认文本作为唯一事实源，旧版本立即失效。

### 5.2 由平台确定性投射 Prompt

优先避免让生成模型负责创作或重写正式 Prompt。建议由平台把确认后的原文确定性写入 Runtime 配置，再让生成代码只负责读取配置。

示例：

```python
PLATFORM_SYSTEM_PREFIX = "平台不可覆盖的安全规则……"

USER_SYSTEM_PROMPT = (
    "面向员工的公司政策咨询与请假调休办理助手，"
    "用对话方式解答政策问题并引导员工完成请假调休申请与查询。"
)

system_prompt = f"{PLATFORM_SYSTEM_PREFIX}\n\n{USER_SYSTEM_PROMPT}"
```

如果使用 JSON/YAML 等配置文件，应由平台序列化正式值，CodeRunner 不得重新生成该字段。

### 5.3 Build 任务携带原文和摘要

Prompt 模块任务应携带至少以下确定性输入：

```json
{
  "systemPrompt": "用户确认的完整原文",
  "systemPromptSha256": "sha256:..."
}
```

Hash 用于绑定任务与正式版本，原文用于写入和验收。不能只传 Hash，因为 Hash 无法恢复或验证生成代码中的实际字符串。

### 5.4 增加生成后确定性等值校验

Prompt 模块完成后，验收器必须读取生成应用最终使用的用户 System Prompt，并与正式 Contract 做严格等值比较。

校验应比较解析后的运行时字符串，而不是直接比较 Python 源码文本。以下源码换行拼接可以接受：

```python
USER_SYSTEM_PROMPT = (
    "第一段，"
    "第二段。"
)
```

只要解析后的值与 Contract 原文完全一致即可。不得接受语义相似、编辑距离接近或模型判断“含义一致”。

### 5.5 不一致时阻断任务完成

校验失败时，Prompt 模块不得进入 `completed` 或 `already_satisfied`，应返回明确且不泄露敏感内容的结构化错误：

```text
Agent Prompt 契约校验失败：生成应用中的 System Prompt 与用户确认配置不一致。
禁止自动接受语义近似或改写后的 Prompt。
```

修复只能恢复正式原文，不能再次调用模型生成一个“更接近”的版本。

## 6. 验收标准

- 用户确认后的 `systemPrompt` 在生成应用运行时逐字一致；
- 允许源码转义、引号形式和相邻字符串拼接不同，但解析后的 Unicode 字符串必须相等；
- 平台安全前缀与用户 Prompt 分开存储和校验；
- 重新生成、自动修复和断点恢复后不得发生 Prompt 漂移；
- Prompt 不一致时必须阻断该模块完成，不能只记录警告；
- 自动化测试至少覆盖原样写入、同义改写、删句、增句、标点变化和源码分段拼接；
- Contract Hash、Prompt Hash、生成文件和实际运行时值能够形成可追踪证据链。

## 7. 当前范围

本文只记录待优化设计和验收标准，本次不修改 Agent 代码生成、TechnicalPlan、Build DAG、CodeRunner 或工程验收逻辑。后续排查到的新问题可继续按新的优化事项编号追加到本文。

## 8. OPT-20260911-002：Agent 代码生成 Token 分批优化

### 8.1 当前状态

本事项已完成方案评审，暂不实施。主分支存在较大变化，后续应先基于合并后的最新生成链路重新核对调用边界，再统一修改，避免在旧结构上形成重复实现或合并冲突。

当前 Agent 生成 Token 消耗的主要结构性来源包括：

- 一个业务 Agent 被编译为 Prompt、Model、Memory、Tools、Skills、Knowledge、Context 七个串行模块任务，最多形成七次独立 CodeRunner 会话；
- 每次模块生成都携带完整 Agent Contract，而任务 `source_refs.agent_contracts` 中又包含一份完整 Contract，形成同一请求内重复；
- 非 Tools 模块也可能携带 Tool Binding 引用的完整 Java API Contract 和 Schema；
- Deep Agent 在读取 Skill、参考文档、模板源码、修改文件和确认结果时产生多个模型回合，后续回合会继续携带此前上下文与工具结果；
- 相同 Skill 和模板公共文件可能被不同模块重复读取；
- 失败后的重试、Repair Planner 和修复任务会再次携带任务、错误、Contract 与代码上下文；
- 当前 Agent Runtime CodeRunner 缺少按模块、按模型回合统计的 Token 明细，无法直接量化各项占比。

### 8.2 优化原则

- 先建立可观测基线，再减少输入上下文，最后减少模型调用次数；
- 七模块任务身份、确认状态和独立验收证据继续保留；
- 正式 Agent Contract 仍是唯一事实源，不因节省 Token 降低实现准确性；
- 不放宽 `allowed_paths`、模板路径策略、Java Gateway 或安全边界；
- 不引入自动循环调试；达到调用或 Token 预算后应停止并交给用户判断；
- 每一批优化应能独立验收，后续批次必须使用上一批采集的真实数据评估收益；
- 按当前契约直接演进，不长期保留旧输入格式、兼容分支或双写逻辑。

### 8.3 第一批：建立 Token 用量基线

先解决“Token 实际消耗在哪里”的问题，不改变生成内容、任务调度和验收行为。

按 Agent、模块和模型回合记录：

```text
run_id
agent_id
agent_module
model_call_count
tool_call_count
input_tokens
cached_input_tokens
output_tokens
prompt_chars
tool_result_chars
duration_ms
retry_count
final_status
```

第一版只写结构化后端日志，不新增产品接口或工作区存储格式。日志只记录计数、模块、状态和必要 Hash，不记录 Prompt、API Key、工具结果正文或源码正文。模型 Provider 不返回 usage 时必须记录为 `unavailable`，不能按零处理。

验收要求：

- 能按一次 Agent 开发运行汇总总 Token；
- 能按七模块拆分输入、缓存输入和输出 Token；
- 能区分初始请求、工具回合、重试和修复调用；
- 观测代码不得改变原始 Prompt、模型参数和生成结果。

### 8.4 第二批：删除单次请求内的重复数据

给 CodeRunner 构造专用的精简任务投影。持久化 Build Task 可以保留完整恢复信息，但发给模型的任务只包含：

```json
{
  "task_id": "agent:leave_assistant::prompt",
  "agent_id": "leave_assistant",
  "agent_module": "prompt",
  "module_config_sha256": "sha256:...",
  "template_commit": "...",
  "allowed_paths": [],
  "engineering_context": {}
}
```

从模型输入中的 `Approved tasks` 删除：

- `source_refs.agent_contracts` 中重复的完整 Contract；
- 调度时间、前端展示字段和历史执行状态；
- 与代码生成无关的验收和恢复元数据。

正式 Agent Contract 在一次请求中只出现一份。JSON 投射使用紧凑序列化，不输出无意义缩进和空白。

验收要求：

- 模型仍能获得一份完整且已确认的正式 Contract；
- Contract Hash、任务身份、模块身份和路径权限不变；
- 单次生成 Prompt 中不得重复出现完整 Contract；
- 生成结果与优化前保持契约等价；
- 目标是初始输入 Token 相对第一批基线至少下降 20%，最终以实测数据为准。

### 8.5 第三批：按模块裁剪正式 Contract

每个模块只接收实现它所需的 Contract 字段：

| 模块 | 允许进入模型上下文的主要内容 |
| --- | --- |
| Prompt | Agent identity、boundaries、persona、正式 System Prompt、constraints |
| Model | Model 配置、requiredCapabilities、generation 参数 |
| Memory | Memory 配置及 thread/checkpoint 相关交互要求 |
| Tools | Tool bindings、相关 capabilities、实际引用的 API Contract |
| Skills | Skills 配置和启用的 Skill ID |
| Knowledge | Knowledge sources 和 retrieval 配置 |
| Context | Context、interaction、security、invocation 相关字段 |

Java API Contract 只允许进入 Tools 模块。Tools 模块也只能获得当前 bindings 实际引用的 Endpoint 及其请求、响应 Schema，不得投射完整后端 API 集合。

验收要求：

- 每个模块具有显式字段白名单；
- 缺少必要字段时确定性失败，不能让模型猜测；
- 非 Tools 模块输入中不出现 Java API Schema；
- CodeRunner 不得自行读取完整规划文件绕过裁剪边界；
- Tools 模块仍能保持 Tool、Endpoint 和 Schema 身份一致。

### 8.6 第四批：确定性投射不需要模型创作的配置

优先把以下内容从生成式实现改为平台确定性投射：

- 用户确认的 System Prompt 原文；
- Model 参数；
- 显式关闭模块的跳过结果；
- 模板已完整支持的默认 Memory 配置；
- Contract Hash、配置 Hash 和固定配置文件。

本批应与 `OPT-20260911-001` 联动：System Prompt 由平台原样写入并做严格等值校验，模型不再负责重新表达正式 Prompt。

如果模板现状已经满足某模块，平台只能基于模板 Commit、文件 Hash、配置 Hash 和确定性检查判定 `reuse`，不能直接信任模型自报。

仍保留模型处理真正需要代码推理的内容，例如业务 Tool 参数映射、新 Tool Adapter、特殊 Context 组合逻辑和聚焦测试。

验收要求：

- System Prompt 逐字落地；
- 确定性完成或复用的模块不调用模型；
- `reuse` 具有可复核的磁盘证据；
- 已关闭模块继续保持 `already_satisfied`；
- 不得用确定性投射掩盖模板能力缺失。

### 8.7 第五批：共享 Skill 与模板静态上下文

不直接使用持续增长的七模块长期对话，而是在一次 Agent 开发运行内建立可失效的静态上下文胶囊：

```text
template_commit
template_policy_sha256
相关文件 Hash
模板能力摘要
已加载 Skill Hash
```

Skill 路由和模板公共结构只确定一次。每个模块仍读取自己可能修改的真实源文件；文件发生变化后，相关摘要和 Hash 必须立即失效并重新计算。

验收要求：

- 同一运行中相同 Skill 和模板公共文件不重复读取；
- 不复用旧模板或旧 Contract 的上下文；
- 不把源码全文长期保存进任务状态；
- 模块开始前仍能获取当前磁盘真实内容。

### 8.8 第六批：合并模型执行批次

前五批稳定后，再根据真实用量考虑减少模型调用次数。七个逻辑任务继续保留，可按同一 Agent、路径锁兼容和依赖完整的条件合并为更少执行批次：

```text
批次一：Prompt + Model + Memory + Context
批次二：Tools
批次三：Skills + Knowledge
```

显式关闭或已由平台确定性满足的模块不进入模型批次。一次调用仍必须返回每个逻辑任务的独立结果，不能把批次整体成功直接映射为全部模块成功。

验收要求：

- 不跨 Agent 合并会话；
- 七模块状态、错误和验收证据保持独立；
- 任一模块失败不能把同批其他模块误标成功；
- 每个模块继续遵守自己的 `allowed_paths`；
- 在常规模块组合下，将最多七个模型执行批次降低至约二至三个，最终数量以契约和实测为准。

### 8.9 第七批：限制修复和重试成本

修复请求只携带失败模块所需的最小增量上下文：

```text
失败模块配置
相关文件 Diff
确定性验收错误
上一次任务结果
允许修复的路径
```

修复不得重新携带完整 Agent Contract、所有 API Schema、全部历史任务或无关工具结果。

按模块配置硬性预算：

- 最大模型调用次数；
- 最大输入 Token；
- 最大输出 Token；
- 最大工具调用次数；
- 最大读取文件字符数；
- 最大修复次数。

达到任一预算后立即停止当前模块，并向用户展示停止原因、已消耗用量和可继续处理的建议，不得自动循环。

验收要求：

- 修复只处理失败模块；
- 已成功模块不重复执行；
- 达到预算后状态明确且可恢复；
- Token 耗尽和业务实现失败使用不同错误类型；
- 手动继续时只恢复用户指定的失败任务。

### 8.10 推荐实施顺序与启动条件

```text
用量统计
  → 删除重复 Contract
  → 按模块裁剪上下文
  → 确定性配置投射
  → 共享静态上下文
  → 合并模型执行批次
  → 修复预算控制
```

开始实施前必须重新核对主分支中的 Agent Build 调度、任务结构、CodeRunner、工程验收和 Tool Activity 入口。若主分支已改变上述职责，应以最新当前契约重做文件级实施计划，不直接套用本文记录的旧文件位置。
