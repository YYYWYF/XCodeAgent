## 先读：这几个词在本文中的意思

先用一句话概括：这个节点读取已经确认的需求/设计和当前工作区，生成一份 Build 任务清单；清单通过检查后先交给用户确认，确认后才真正执行。

| 词 | 白话解释 |
| --- | --- |
| DAG（任务依赖图） | 由执行任务及其依赖边组成的有向无环图。例如“先生成 API 客户端，再实现调用它的页面”。 |
| 执行任务（Task） | Build 阶段实际执行的一项具体工作，例如实现一个接口或页面。 |
| Build（任务执行阶段） | 按已确认的任务计划实际修改项目代码并完成任务的阶段。 |
| 职责分组（Unit） | 生成任务计划时的一类职责范围，例如一个页面或一个接口；它可以产出一条或多条执行任务，本身不是执行任务。 |
| 正式任务计划 | 经用户确认后可供 Build 执行的任务计划，存储在当前工作区的 `.devagentstudio/plans/build-task-plan.json`。 |
| 待确认任务计划（PendingPlan） | DAG 生成和全局校验通过后交给用户审核的计划。它合并正式基线中保留的任务与本轮候选任务；未经确认不能交给 Build 执行，存储在当前工作区的 `.devagentstudio/drafts/plans/build-task-plan.pending.json`。 |
| 候选任务（Candidate） | 一个职责分组在当前 PlanningRun 中产生或恢复的任务增量。候选先通过单Unit内部校验，再与其他必需候选任务组装并通过全局校验；只有待确认任务计划经用户确认后，任务才进入正式计划。 |
| PlanningRun（一次任务生成运行） | 从读取冻结输入到写入待确认任务计划或运行失败的一次运行对象，由当前进程中的 Controller 管理。产物文件`.devagentstudio/plans/planning-run.json` 只保存轻量进度投影，不含候选任务正文，也不能恢复完整运行。 |
| 计划生成服务 | `build_task_planning_service.py` 中的后端业务逻辑，负责创建 PlanningRun、调用生成流程并保存待确认计划；它不是独立部署的服务进程。 |
| 目标范围（Scope） | 本次任务生成的目标，可以是整个应用、某个页面或某个 API。 |
| Reuse（复用） / Capability（能力） | 检查当前正式计划里是否已有明确承担某项职责的任务。Capability 是任务声明“我提供/需要什么能力”的字段；判断依据是这些声明和归属，不是描述文字看起来相似。 |
| 确认（`Confirm`）/ 重新生成（`Regenerate`）/ 放弃（`Abandon`） | 分别确认当前待确认任务计划、消费当前计划后重新生成、放弃当前待确认计划。 |
| 候选恢复（Recovery） | 工作流按明确的旧执行来源重试或从中断处续接时，尝试复用旧候选任务。恢复会创建新的 PlanningRun；候选必须通过来源身份、当前输入和职责分组校验。 |
| 输入指纹 | 平台对本次规划的完整冻结输入计算的摘要，包括正式产物、正式任务基线、职责骨架、目标范围、工作区上下文、复用事实和正式接口来源等；用于核对规划与确认阶段读取的输入是否一致，用户不需要提供。 |
| 单Unit内部校验（Local Validation）/ 全局校验（Global Validation） | 前者校验一个职责分组产生的候选任务；后者校验组装后完整任务图的依赖与规则。 |
| 正式接口契约（API Contract） | 一组正式接口说明，例如 `orders-api`；其中列出后端操作及请求方式、路径和约束。契约编号是该定义的稳定标识。 |
| 接口操作（Endpoint）/ 接口设计 | 接口操作是正式接口契约中的一项具体请求，例如 `orders.list` 对应 `GET /orders`；接口设计进一步说明该操作如何读写数据或调用外部服务。 |
| AG-UI | 项目在前后端之间传递工作流进度、用户动作和结果的消息协议。 |
| 数据源类别 / 数据源实例 | 类别是数据库、外部 API 等类型；实例是某个具体数据源编号、数据库连接或 API 服务地址。两个数据库属于同一类别，但属于不同实例。 |

本文保留源代码中的英文状态名、字段名和类型名，方便定位实现；普通说明统一使用“职责分组”“候选任务”“执行任务”“待确认任务计划”等中文术语。用户界面不展示原始职责分组类型名或 `unit_id`，展示名称遵循 [Build 任务单元语义化文案](design/build-task-unit-labels.md)。

## 1. 模块位置、输入输出与边界

### 1.1 在工作流中的位置

从用户操作看，这段逻辑位于 Build 真正开始前：先准备要执行的任务清单。项目使用 LangGraph 作为工作流框架，它会根据每一步结果选择下一步要执行的内容。常规主线先经过 API 设计就绪门禁，确认本次目标所需的接口设计有效；随后检查工作区，再调用 `prepare_build_tasks` 节点。节点重新读取并核对正式输入，生成待确认计划；用户确认后，计划才进入正式状态并交给后续 Build 流程。

~~~mermaid
flowchart LR
    A[检查本次目标的 API 是否已有正式设计] --> B[检查工作区]
    B --> C[prepare_build_tasks 生成任务计划]
    C -->|计划检查通过| D[等待用户确认]
    D -->|确认计划| E[保存为当前正式计划]
    E --> F{是否需要权限初始化?}
    F -->|需要| G[执行权限初始化]
    F -->|不需要| H[build]
    G --> H
    D -->|重新生成| C
    D -->|放弃计划| I[结束当前待确认计划]
    C -->|生成失败| J[本次计划运行失败]
~~~

下面几个文件分别负责工作流接线、读取输入、安排生成和保存计划：

- [workflow.py](../Backend/app/graph/workflow.py)：把 `prepare_build_tasks` 放进整条工作流，并决定下一步去确认、Build 还是返回错误。
- [task_planning_adapter.py](../Backend/app/graph/nodes/task_planning_adapter.py)：把工作流传来的输入和 `Confirm` / `Regenerate` 等动作转交给相应处理逻辑。
- [task_planning_inputs.py](../Backend/app/graph/nodes/task_planning_inputs.py)：读取并核对节点生成任务所需的前置产物、当前目标和现有正式任务。简单说，就是“这个节点从哪里拿输入、如何确认输入可用”。
- [build_task_planning_service.py](../Backend/app/services/build_task_planning_service.py)：创建一次 PlanningRun、调用生成流程，并在成功后把待确认计划写入工作区文件的后端业务模块。
- [dag_planning_orchestrator.py](../Backend/app/services/dag_planning_orchestrator.py)：调度职责分组生成、检查和修复的先后步骤。

### 1.2 主要输入

1. 前置产物和本次目标所需的接口设计：RequirementSpec（需求说明文档）、ProductPlan（产品规划文档）、UiManifest（UI 设计结果）和 TechnicalPlan（技术规划方案）。节点按各产物的规则检查确认状态（例如 UiManifest 也允许 `skipped`），并重新计算 `basedOn` 所引用的直接上游内容摘要；页面或接口目标还要检查相关接口设计已确认且仍有效。这不要求所有文件使用相同的版本号。
2. 当前应用工作区的模板、文件和资源就绪情况。代码把生成时需要的这组工作区信息称为 BuildContext。
3. 当前正式任务计划，作为已有任务的起点。文件不存在表示首次生成；文件存在但内容不合法时，节点报错，不会把它当作空计划继续生成。
4. 本次任务生成的目标范围、哪些已有任务能承担所需工作的记录、职责分组，以及模型可查阅的只读接口契约目录（`Frozen Contract Catalog`）。目录提供接口操作、数据来源和约束等信息；模型只能通过受限读取工具调用查看当前职责分组相关内容。
5. 本次运行的身份（会话、工作流运行和对话线程），以及模型配置、超时、并发数和上下文长度预算。

在第一次调用模型前，节点会冻结本次规划所需的完整输入并计算输入指纹。后续确认时，服务端会重新读取正式输入；如果正式产物、目标范围、工作区上下文、复用事实或正式任务基线等冻结内容发生变化，输入指纹就不会匹配，待确认计划不能直接升为正式计划。不同职责分组只会收到相关上下文；接口契约正文由受限读取工具按需提供，不会把全部产物都交给每个职责分组。

### 1.3 输出与不负责的事情

- 成功时，输出的产物是**待确认任务计划**。节点会保留原计划中的任务，把本次新任务加进去，组成完整的任务依赖图；通过全局检查后写入待确认任务计划。写入成功后，交给用户确认；经用户确认后成为正式任务计划，Build 读取并执行其中的任务。
- 失败时，符合支持恢复条件的职责分组模型调用故障，且失败运行中至少已有一个有效候选任务时，系统会尽力写入 `.devagentstudio/runtime/planning-recovery/{workflow_run_id}.json`；其它错误不会有，因此失败后不一定有该文件。它是内部的候选复用优化材料，不是完整运行快照，也不向用户展示。
- 成功与否都会写入的文件是 `planning-run.json`，该文件保存最近一次 PlanningRun 的轻量进度和错误投影。

## 2. 完整生成流程

~~~mermaid
flowchart TD
    A[核对前置产物与工作区] --> B[确定本次目标和所需的职责分组]
    B --> C[读取已确认任务并判断哪些执行任务可复用]
    C --> D[计算各职责分组仍缺少的工作]
    D --> E[固定本次生成使用的输入和接口契约]
    E --> F{是否有可复用的旧候选任务?}
    F -->|可以安全复用| G[采纳旧候选任务]
    F -->|没有或校验失败| H[为该职责分组安排新生成]
    G --> I[并发生成其余缺失候选任务]
    H --> I
    I --> J[等待所有计划生成分组完成本轮]
    J --> K{每个计划生成的分组都有有效候选?}
    K -->|没有| L[把缺失候选转成可修复的全局问题]
    L --> M{问题可归因且仍有修复额度?}
    M -->|可以| N[重新生成缺少候选的分组]
    N --> J
    M -->|不可以| O[本次 PlanningRun 失败]
    K -->|都有| P[保留正式任务并加入有效候选]
    P --> Q[编译并检查完整任务图]
    Q -->|有可归因问题且仍有修复额度| R[重新生成对应分组]
    R --> J
    Q -->|检查通过| S[写入待确认任务计划]
    Q -->|不可归因、不可修复或额度耗尽| O
~~~

当前生产步骤：

1. **核对输入**：确认需求文档、产品规划、UI 设计、技术规划和接口设计可用于当前目标；读取工作区模板和文件是否就绪。
2. **确定范围**：把“整个应用 / 指定页面 / 指定接口”转换为本次需要准备的职责分组和工作区上下文。
3. **检查现有任务**：读取当前已确认任务计划，依据任务明确声明的职责，判断哪些工作已经完成规划、可以沿用。
4. **列出缺项**：对每个职责分组逐项判断还缺哪些工作，不根据任务描述的相似度猜测。
5. **固定输入**：冻结本次规划使用的正式内容、目标范围、工作区快照和复用事实，建立各职责分组的模型输入，并限制它们只能读取相关接口资料。所有职责分组准备完毕后才发起模型请求。
6. **生成候选任务**：（1）平台按固定规则直接产生的任务不调用模型（例如权限资源点注册）；（2）需要模型产出候选任务的职责分组进入有并发上限的队列；（3）职责分组复用：恢复上下文明确绑定了某个旧工作流执行，且该执行的候选任务通过当前输入和职责分组检查，会跳过这些职责分组的重新生成，具体门槛见 7.3。
7. **等待本轮结束并检查候选完整性**：代码把等待点称为 `Generation Barrier`，所有计划生成的职责分组都生成有效候选时，会组装完整的待确认计划。因此，需要每个计划生成的职责分组都要结束当前轮次（生成有效候选任务或者耗光生成次数）；如果某个职责分组用完单组尝试机会仍没有有效候选，它会被记为“候选缺失”，后续可能进入全局修复。
8. **组装完整计划**：保留正式任务计划中的任务，加入本轮有效候选任务，再按权威职责分组依赖编译任务依赖，并记录确认页所需的“新增 / 复用”分类。
9. **全局检查与修复**：检查完整计划；只有明确能归属到某些新生成职责分组的问题，才允许按修复预算重新生成这些职责分组，然后再次组装和检查。
10. **保存待确认计划**：所有检查通过后，把待确认任务计划写入当前应用工作区，展示给用户审阅。

关键实现：[dag_planning_orchestrator.py](../Backend/app/services/dag_planning_orchestrator.py)、[scope_assembly.py](../Backend/app/services/scope_assembly.py) 和 [build_task_planner.py](../Backend/app/services/build_task_planner.py) 中被组装器调用的 `compile_build_task_plan_scope`。其中 `create_build_task_plan` 不在当前主线调用链中。

## 3. 职责分组、依赖关系与执行任务

职责分组（Unit）表示由同一组输入和生成规则负责的一类工作；执行任务是 Build 阶段按照计划任务依次开展代码实现。

在最终的正式任务计划（`.devagentstudio/plans/build-task-plan.json`）中，有两类依赖关系：（1）职责分组依赖图（unit_graph）表达分组之间的关系，（2）任务依赖图（task_graph）表达具体执行任务之间的先后关系，二者粒度不同。

### 3.1 当前职责分组类型

标准职责分组清单由 [build_unit_skeleton.py](../Backend/app/services/build_unit_skeleton.py) 建立；各组具体要完成什么由 [unit_generation_requirements.py](../Backend/app/services/unit_generation_requirements.py) 计算。

| 职责分组 ID（内部） | 生成方式 | 职责说明 |
| --- | --- | --- |
| `application:root` | 只作结构节点，不生成任务 | 当前应用任务图的根。 |
| `frontend:shell` | 只检查前置条件 | 检查前端模板和基础页面框架是否就绪；暂时不生成相关任务，后续可扩展框架层任务。 |
| `frontend:api-client` | 先复用；缺少时由模型生成 | 前端调用后端接口的共享模块，按接口契约归组。同一契约下，本轮需要新增的多个操作可由一个前端任务写入同一模块；每项操作按契约 ID 与接口操作 ID 单独识别，并在任务计划中只归一个任务负责。例如，`orders-api` 这份接口定义可以包含 `GET /orders`、`POST /orders` 和 `DELETE /orders/{id}` 等不同操作；前端请求函数可以集中在 `frontend/src/apis/ordersApi.ts`。它们可以共用一个按接口契约组织的模块，但每项操作仍按契约 ID 和接口操作 ID 单独识别，并在计划中明确实现归属。 |
| `frontend:auth-guard` | 先复用；缺少时由平台按规则生成 | 把已确认的权限资源列表写入前端资源文件，不调用模型。 |
| `backend:bootstrap` | 先复用；缺少时由模型生成 | 后端共用的数据库或外部 API 初始化职责；按来源类别归组，不按每个具体数据源实例建立分组。 |
| `backend:endpoint:<apiContractId>:<endpointId>` | 先复用；缺少时由模型生成 | 一个后端接口的实现。例如 `orders-api` 契约中的 `orders.list`，请求为 `GET /orders`；职责由契约 ID 和接口操作 ID 共同标识。 |
| `page:<pageId>` | 先复用；缺少时由模型生成 | 一个页面的实现；引用该页面依赖的接口操作和页面设计约束。 |
| `app:integration` | 只作结构节点，不生成任务 | 汇总页面和后端实现的集成节点。 |

> 表中的“先复用；缺少时由模型生成”是生成策略的简称：只有现有正式任务明确满足相同职责时才复用，否则才创建新的候选任务。

### 3.2 分组依赖图不等于模型运行顺序

代码中的职责分组依赖图表达工作层级和分组依赖，例如：

- 应用根节点（application:root）包含本次目标要用的分组；
- 后端初始化（backend:bootstrap）指向本次要实现的后端 API 分组；
- 后端 API 分组也可以连接到集成汇总节点（app:integration）；
- 页面分组在职责依赖图中可以关联前端基础框架、API 客户端、权限资源和后端 API 分组；不过编译页面任务依赖时，页面只继承前端域依赖，不会等待后端 API 实现。
- app:integration 汇聚页面和后端实现。

这张分组依赖图用于平台计算任务依赖，不代表模型会按图上的顺序逐个运行。生产调度器按排队先后派发待生成分组，最多同时运行 3 个模型请求。之后，平台再根据分组依赖和每条执行任务的依赖字段，计算出具体任务的执行先后关系。

候选中的显式任务依赖只能指向本组候选任务，或上下文明确列出的同组正式保留任务；指向其他职责分组任务会在单Unit内部校验时被报告为错误，不会作为有效关系悄悄接受。编译器还会防御性地移除遗留的跨组显式任务依赖，再依据权威职责分组依赖图生成合法任务依赖。页面任务有前端并行策略：只继承前端域依赖，不等待后端接口实现；前后端一致性留给后续集成检查。

### 3.3 一个职责分组可以生成多条执行任务

模型生成的执行任务记录包括几组信息：

- **归属**：`id` 是任务编号，`unit_id` 表示它属于哪个职责分组。`owner` 表示实现归属领域：`frontend`（前端）、`backend`（后端）或 `database`（数据库），这个字段会在 Build 执行时用于选择相应的实现执行器。`task_type` 是任务类别，例如 `frontend.code` 或 `backend.code`，与 `owner` 不同。
- **工作内容**：`title` 和 `description` 说明要做什么；`deliverables` 列出要交付的内容；`dependencies` 列出必须先完成的任务。
- **文件范围**：`target_files` 列出预计要改动的仓库文件；`change_scope` 说明对文件要新增、修改还是删除；`allowed_paths` 是允许任务写入的仓库文件范围。这些是代码文件路径，不是 API URL。平台会规范路径，并在缺少允许范围时用目标文件补齐；新增还是修改也会结合当前工作区中的文件情况确定。
- **执行和复用信息**：`execution_strategy`、`platform_executor` 描述执行方式；`requires_capabilities` / `provides_capabilities` 分别说明需要和提供的能力；`risk`、`approval`、`source_refs` 保存风险、审批和来源信息。

状态和并行信息由平台在组装任务计划时设置或计算：

- **状态 `status`**：新任务初始为 `pending`，意思是“等待 Build 执行”。执行期间会变成 `running`，结束后记录为 `completed`、`already_satisfied`（现有代码已满足要求）或 `failed` 等结果。它表示任务进度，不是任务类别。
- **并行信息**：平台根据任务依赖和目标文件是否重叠，计算 `can_run_in_parallel`、`parallel_with`、执行方式和任务批次。依赖未完成的任务要等待；目标文件冲突的任务不会放进同一并行批次；其他互不冲突的任务可以并行。这里说的是 Build 执行阶段的执行任务并行，不是 DAG 生成阶段同时发起模型请求的数量。

实际字段和规则以 [build_task_planner.py](../Backend/app/services/build_task_planner.py)、[unit_candidate_validator.py](../Backend/app/services/unit_candidate_validator.py) 和 [task_scheduler.py](../Backend/app/services/task_scheduler.py) 为准。

一个职责分组可以产出多条执行任务；一条执行任务也可以覆盖该职责分组内多个相关交付物。接口操作的后端实现常见拆分为：

- `backend.endpoint.objects`：描述接口输入和输出的数据结构。
- `backend.repository`：需要读写数据库时负责访问数据库的模块。
- `backend.upstream`：需要调用外部 API 时负责发起调用的模块。
- `backend.application_service`：组合业务步骤和数据结果的模块。
- `backend.endpoint_controller`：接收 API 请求并转交给业务模块的入口。

当前的职责与提示规则为混合来源 API 操作规定了这样的任务结构：`repository` 访问数据库，`upstream` 调用外部 API，`application_service` 汇合两条分支，`endpoint_controller` 接收请求并调用业务服务。这描述的是平台提供给模型的生成合同；它不保证每次模型实际输出都符合合同，测试覆盖范围见 6.3。

## 4. 候选任务的生成、上下文与来源

### 4.1 候选任务的身份和来源记录

`CandidateAttempt` 是平台保存的一条候选记录，包含候选任务正文、状态、当前归属身份和来源。`candidate_id` 唯一标识这条记录；其中的 `CandidateIdentity`（`planning_run_id`、`unit_id`、`generation_round`）表示它属于哪次运行、哪个职责分组和哪一轮，不是候选记录的唯一 ID。当前来源类型为 `generated` 或 `recovered`：

- 模型生成的候选通过 `generated_from` 指向一次实际模型调用的 `AttemptIdentity`。该身份还包含独立的 `attempt_id`，不能用任务 ID 或候选 ID 代替。
- `frontend:auth-guard` 由平台按固定规则构造任务；其候选记录仍标为 `generated`，并关联一次确定性生成的 dispatch 身份，但不调用模型、不消耗模型内容重试额度。任务的 `execution_strategy` 标为 `deterministic`。因此看到 Attempt 身份不能单独推断发生过模型调用。
- 恢复来的候选通过 `recovered_from` 指向旧 PlanningRun 和旧 `candidate_id`。采纳后会分配新的 `candidate_id`，并取得当前 PlanningRun 的身份；它不会伪造当前运行中的模型调用，也不扣除模型内容重试次数。
- `CandidateAttempt.status`（`valid`、`invalid`、`superseded`）描述候选记录本身；`UnitRunState.generation_status`（例如 `candidate_ready`、`round_exhausted`）描述职责分组的生成进度，两者不是同一个状态。

这些来源记录见 [unit_generation_contracts.py](../Backend/app/services/unit_generation_contracts.py)；合法状态之间的约束见 [planning_run_contracts.py](../Backend/app/services/planning_run_contracts.py)。

### 4.2 模型每次请求能看到哪些内容

职责分组上下文绑定当前 PlanningRun、输入指纹、已确认任务计划的摘要、目标范围、职责分组身份和正式职责。它包括：

- 当前职责分组的生成职责和目标文件边界；
- 相关职责分组依赖；
- 该职责分组已保留任务的必要摘要，以及接口操作的唯一实现归属限制；
- 当前只读 API 资料目录中允许访问的引用；
- 本轮需要新增的职责。平台会先按职责分组逐项核对：旧正式任务明确声明的能力/交付物、精确对应的既有接口实现任务，或平台验证过的工作区能力，能够覆盖某项职责时，这项职责就不再要求生成。因此可能只复用一个职责分组的部分职责，也可能整个职责分组的职责都已满足。模型最终收到的是尚未满足的职责列表（`generation_requirements`）；已有任务摘要和接口归属约束会作为上下文提供；
- 本轮检查发现的具体问题，供重新生成时修正。

模型必须通过受限读取工具调用读取接口资料；`selector`（资料选择条件）用来选取内容，`cursor`（续读位置）用来指定分页时从哪里接着读。系统限制每个职责分组可读取的资料数量。输入内容或资料存储损坏属于平台故障，不是模型写错格式，不能按普通内容错误重试。

### 4.3 候选任务还不是用户确认的计划

候选任务只是一个职责分组产生的临时任务结果。每个结果都通过职责分组内部检查后，还要等所有职责分组的任务生成完成、组装全局任务图并通过全局检查，系统才保存待确认任务计划。用户确认当前待确认任务计划后，它才成为正式任务计划。

`planning-run.json` 是 PlanningRun 的轻量状态快照，只保存进度、状态和错误，不保存完整候选任务内容。因此它可以用于查看进度和排障，但不能单独接着执行原来的完整生成运行。失败恢复文件和中断续接文件是另外的证据，各有单独来源身份和复查规则。

## 5. 哪些旧任务可以沿用

判断依据是当前已确认的正式任务计划、任务明确声明的能力，以及平台能够核实的归属/工作区信息。任务状态或两段描述文字相似，都不足以证明任务能满足某项职责。实现见 [build_task_reuse.py](../Backend/app/services/build_task_reuse.py)。

- 原正式任务计划中的任务会保留下来；任务当前是已完成、待执行还是失败，不单独决定它是否满足某职责。
- 可复用能力（Capability）必须写在明确的 `provides_capabilities` 或 `deliverables` 字段中。
- 接口实现归属根据接口定义 ID 与具体接口操作 ID 的精确组合判断。
- ReuseFacts 是平台针对“哪些旧任务能满足哪些职责”形成的记录。缺少证据时不猜测，也不按部分相似度回退。
- 组装时原任务保留、新任务追加。若新旧任务 ID 冲突就停止，不自动改名或合并。
- 生成待确认计划时，平台会记录本轮新加入的任务、实际满足本轮职责的旧任务，以及确认页需要展示的任务编号。该分类记录只保存在工作区的 Pending JSON 中，供程序读取：

  | 字段 | 含义 |
  | --- | --- |
  | `new_task_ids` | 本轮新加入待确认计划的任务编号，包含模型生成和平台按固定规则生成的任务。 |
  | `reused_task_ids` | 本轮确实用来满足当前职责的旧正式任务编号；仅仅留在累计计划里不算复用。 |
  | `platform_task_ids` | Pending provenance 中用于排除确认页普通审阅的任务编号。当前主线的 Scope Assembly 将该集合设为空；不能据此认为确定性生成的权限资源任务会被隐藏。 |
  | `review_task_ids` | 确认页要展示的任务编号；其中本轮新任务标为“新增”，旧任务标为“复用”。 |

  确认页根据这些编号展示任务和“新增 / 复用”标记，不从任务标题或描述猜来源。这个字段存在于工作区的 Pending JSON（`.devagentstudio/drafts/plans/build-task-plan.pending.json`），不是用户要编辑的 Markdown 内容；Pending 确认并写入 Formal 时会移除。字段缺失、任务编号对不上或分类关系不合法时，确认页报错并要求重新生成，而不是自行推断。

  当前 `frontend:auth-guard` 的确定性任务也作为候选任务进入 `review_task_ids`，所以会在确认页显示为“新增”。这和 4.1 中记录在候选上的来源身份不同：这里的分类只决定确认页如何展示任务。

需要区分**任务保留**和**职责复用**：任务保留表示旧条目继续留在累计计划中；职责复用表示旧任务的明确能力满足了这次目标中的某项要求。保留任务本身不会自动满足新职责。

## 6. 对单个职责分组任务和整张任务图的校验

这里的校验器指平台的自动检查规则。单个职责分组校验针对一个职责分组生成的候选任务；全局校验针对所有任务合并后的完整任务图。出现问题后，平台还会判断能否归因到有限个职责分组，如果可以，会重新生成这些分组，之后再次开展校验。

### 6.1 单个职责分组候选校验

候选任务通过以下单组检查后，候选记录状态会成为 `valid`；对应职责分组的 `generation_status` 才会进入 `candidate_ready`：

1. 模型返回的文本能否解析成规定的任务 JSON 格式。
2. 每条执行任务的必要字段和交付物是否齐全。
3. 任务归属、目标文件和允许修改路径是否在该职责分组与本次目标范围内。
4. 该组职责是否覆盖完整，有没有越权实现其他 API 或页面的工作。
5. 执行任务之间的依赖是否符合允许清单，是否错误跨组或形成循环。
6. 复用任务归属、API 定义/交付物边界和平台规则是否满足。

只有当所有问题都被标记为“当前职责分组的生成内容错误”、允许重试且只涉及这个职责分组时，系统才重新请求模型修改这一组结果。输入、平台、接口契约来源错误，或不能安全确定责任归属的问题，会终止本次 PlanningRun。

### 6.2 全局任务图校验

所有需要产出候选任务的职责分组都有有效候选、并完成全局组装后，平台检查完整任务依赖图，包括：

- 任务 ID、执行角色、所属职责分组和本次目标范围是否一致；
- 所依赖的任务是否存在、先后顺序是否有效、是否有循环；
- 职责分组依赖是否允许，以及跨组依赖是否与平台计算的一致；
- 每个接口操作是否只有一个实现归属，已确认接口定义要求是否有对应任务；
- 模板、权限、后端初始化和目标文件限制；
- 工程检查与业务验收条件是否齐全；
- 是否符合 v4 版任务计划格式，并能拆分成可执行批次。

平台只会在有明确规则、来源记录或冲突证据时，把全局问题归到可重新生成的职责分组。原计划保留的任务和平台直接生成的任务不会被误判成模型新结果。无法确定应重生成哪组时，系统停止而不猜测。这个归因过程由 [global_issue_attribution.py](../Backend/app/services/global_issue_attribution.py) 实现。

### 6.3 混合数据库与外部 API 的职责及提示规则覆盖

**自动测试覆盖（职责计算和生成提示）**：当单个 API 操作同时需要数据库和外部 API 时，职责计算会要求生成对象、数据库访问、外部调用、业务服务和 API 入口等工作；提示规则中的任务清单要求业务服务依赖数据库与外部调用两条分支。相关用例包括：

- [test_unit_task_prompt.py](../Backend/tests/test_unit_task_prompt.py)：检查模型提示中的任务清单、分支依赖和业务服务汇合规则。
- [test_unit_generation_requirement_targets.py](../Backend/tests/test_unit_generation_requirement_targets.py)：检查一个 API 操作的来源类别如何决定后端职责清单。

这些测试没有调用真实模型，也没有检查模型返回的候选或最终编译出的任务图。因此它们证明的是职责计算和提示合同包含这两类工作及其依赖规则，不证明真实生成结果或 Build 执行一定符合该结构。它们也没有验证多个具体数据库、多个外部 API 地址，或为每个具体数据源分别生成配置和初始化步骤。

## 7. 重试、恢复、失败与清理

### 7.1 三类重试额度

| 机制 | 当前次数 / 触发 | 处理范围 |
| --- | --- | --- |
| 单Unit内容尝试 | 每轮最多 3 次模型调用，含首次调用 | 只重试当前职责分组中可通过改写修正的问题；上一份无效结果会随问题说明一起发给模型。 |
| 模型调用库内部重试（SDK retry） | 生产配置 max_retries=2 | 模型调用库遇到请求错误时自行重试；次数不计入上面的 3 次内容尝试。模型已输出部分文本后若中断，系统不会从中断位置接着读取。 |
| 全局修复 | 最多 2 轮 | 全局任务图校验发现可明确归属到职责分组的问题时，重生成相关分组，再重新组装和全局校验。 |

### 7.2 会终止本次运行的错误

模型初始化或调用基础设施故障、接口契约或读取接口损坏、输入身份或校验摘要不一致，以及不能安全归到职责分组的问题，会使本次 PlanningRun 失败或取消。可重试的内容问题如果每轮最多 3 次模型调用后仍没有有效候选，会被完整性检查标记为“候选缺失”，之后最多进入 2 轮全局修复；不可重试或无法归因的问题仍会直接失败。并发调度器会停止派发新模型请求、取消正在运行的同批请求，并忽略取消之后才返回的结果。失败的 PlanningRun 已结束，不能接着原状态继续执行。

用户或工作流触发整段工作流重试时，会根据当前正式输入新建 PlanningRun；不会从只含进度状态的 `planning-run.json` 还原旧运行。错误阶段名 `model_setup` 表示模型客户端初始化阶段出错，`model_invoke` 表示发起模型调用阶段出错。它们只能说明错误出现在哪段代码，不能单凭标签认定模型供应商有问题；还需查看同一次模型调用的日志、HTTP 状态码、供应商错误、耗时和当前配置。

### 7.3 复用旧候选任务的来源与门槛

这里的“准确来源”有两层，不能用“找到一个最近的候选文件”代替：

1. **旧工作流执行**：`resumeExecutionRunId` 指向具体的一次完整工作流执行。工作流原生恢复机制据此绑定 `source_run_id`；DAG 节点只按这个 ID 读取对应快照。没有这个恢复来源，就不读取旧候选。
2. **快照里的候选**：候选还必须属于快照记载的 `source_planning_run_id`（旧执行中的那次 DAG 生成运行），并通过 `unit_id` 和 `candidate_id` 定位。失败快照由旧 PlanningRun 的 `latest_candidate_id` 指针构造，只收录状态为 `candidate_ready` 的职责分组；候选 ID 必须能在同一个 PlanningRun 中解析。代码不会跨 PlanningRun 按职责分组名称搜索一个“差不多”的候选。

通过来源定位后，还要满足以下门槛：

| 门槛 | 实际核对内容 | 不满足时 |
| --- | --- | --- |
| **1. 本次动作允许恢复** | 旧执行来源由 Workflow 恢复上下文带入，普通 `Regenerate` 本身不会挑选或读取旧失败快照。只有当包含该动作的 Workflow 也正在原生恢复时，后端才会核对原始动作、旧 PlanningRun ID、草稿摘要和目标范围；全部匹配后才传入旧执行来源。 | 没有恢复来源或动作身份不一致时，不读旧快照。 |
| **2. 找到匹配且完整的快照** | 失败重试读取 `.devagentstudio/runtime/planning-recovery/{source_workflow_run_id}.json`；中断续接读取 `.devagentstudio/runtime/planning-interruption/{source_workflow_run_id}.json`。文件内的 `source_workflow_run_id` 必须等于请求的旧执行 ID，快照结构及内容摘要必须有效。失败快照还必须来自支持恢复的职责分组模型调用故障，并至少含一个候选。 | 文件缺失、损坏、ID 不符或错误类型不支持时，按全新生成继续。 |
| **3. 候选本身在旧运行中有效** | 候选的职责分组身份、PlanningRun 和完整输入指纹必须与快照相符；候选状态必须是 `valid`，没有单组检查问题，且任务列表非空。中断续接还要求旧 Workflow 运行 ID、所属会话、活动线程、PlanningRun ID、状态版本号和 `active` 状态与当前保存的运行状态一致。 | 快照整体身份不符时全部放弃；单个候选不符时只放弃该候选。 |
| **4. 旧运行输入仍等于本轮输入** | 将当前生成运行与快照对比：`input_fingerprint`（完整冻结输入摘要）、`base_confirmed_plan_digest`（已确认任务计划摘要）和 `build_execution_scope`（本次目标范围）都必须一致。 | 任一项不同，整份快照过期，本轮不复用其中候选。 |
| **5. 该职责分组当前仍需要生成，并且候选通过当前检查** | 职责分组必须仍在本轮待处理范围中，当前状态为 `pending`，生成策略仍受支持。系统按本轮冻结输入重建职责分组上下文，再用当前的接口契约、依赖上下文和可复用任务事实重新运行单Unit内部校验。 | 职责分组不再需要、上下文无法重建或单组检查出现问题时，只淘汰它的旧候选，让该分组走正常生成。 |

全部通过后，旧任务内容才会作为**属于新 PlanningRun 的恢复候选任务**接纳。新候选会保存来源 PlanningRun ID 和来源候选 ID；系统不会伪造一次不存在的模型调用。之后仍需等所有职责分组齐备、重新组装任务图并通过全局校验，才能写入待确认任务计划；用户确认后才会成为正式任务计划。

失败运行始终是终态：候选恢复只把合格候选作为新 PlanningRun 的输入优化，不恢复或继续修改旧 PlanningRun。输入变化导致整份快照失效；单个候选失效则只重新生成对应职责分组。中断快照只为仍处于 `active` 的 PlanningRun 保存候选，并且必须匹配当前 Workflow 运行身份和版本。

### 7.4 删除与状态清理

Pending 生命周期锁是在同一后端进程内按工作区隔离的可重入锁，保护 Pending 写入、确认、放弃以及重新生成消费旧草稿等提交点；它不跨进程，也不覆盖整段模型生成。`Regenerate` 消费旧 Pending 后会释放锁，再重新读取正式输入并启动新的 PlanningRun。每个动作只处理身份匹配的草稿，不会误删后来生成的新 Pending。清理会话时只清理准确归属该会话且已失败的运行；运行状态成功写入后，才尽力删除对应旧恢复文件。删除恢复文件失败不会推翻已经保存的结果。

## 8. DAG 任务生成的关键条件与常见失败原因

本章描述当前异步生成主线：适配器从工作区重新读取正式产物并冻结输入，规划服务创建新的 `PlanningRun`，随后计算职责、生成并校验候选任务、组装完整任务图。只有全局校验通过后，系统才写入待确认任务计划；生成阶段不会直接修改正式任务计划。

本文统一用“职责分组”描述内部生成和校验边界，代码身份由 `unit_id` 承载；用户界面展示名称遵循 [`docs/design/build-task-unit-labels.md`](design/build-task-unit-labels.md)，不直接展示原始 `unit_id`。

### 8.1 生成准备阶段

#### 8.1.1 DAG 任务生成的门禁

| 条件 | 代码核对 | 不满足时 |
| --- | --- | --- |
| 正式产物存在且处于可用确认状态 | 从当前工作区读取 RequirementSpec、ProductPlan、UiManifest 和 TechnicalPlan；RequirementSpec、ProductPlan 必须为 `confirmed`，UiManifest 必须为 `confirmed` 或 `skipped`，TechnicalPlan 还必须具有正确的 `artifact_type` 并处于 `confirmed`。读取不以工作流检查点内容兜底。 | 生成前阻断，返回具体缺失、未确认或读取错误。 |
| 上游摘要仍然匹配 | 对带有 `basedOn` 的正式产物，重新计算其直接上游文件摘要；摘要不匹配意味着产物需要重新确认。这里核对的是文件内容摘要，不只是版本号。 | 生成前阻断；先修正并重新确认受影响的正式产物。 |
| 当前目标和接口设计一致 | 构建执行范围（`build_execution_scope`）必须能从当前流程状态解析；没有局部目标时默认使用应用范围。页面或接口目标还会检查依赖的接口设计是否齐全、已确认且未失效；随后按当前范围检查 TechnicalPlan/API 契约一致性。 | 门禁暂停并指出缺失或失效的接口设计，或报告范围内的契约问题。 |
| 模板上下文有效 | 必须能读取当前工作区的 `TemplateState` 并编译当前模板上下文。若 `.devagentstudio/application.json` 中 `authorization.enabled` 为 `true`，当前模板有效能力还必须包含 `authorization`。模板上下文随后绑定到本轮规划和待确认计划。 | 生成前阻断；检查 `TemplateState`、应用配置及授权能力是否一致。 |
| 已有正式任务计划可继续使用 | 如果 `.devagentstudio/plans/build-task-plan.json` 不存在，系统按首次规划从空计划开始。如果文件存在，系统会读取并检查它：必须是当前 `build-dag.v4` 格式、已确认，而且任务图校验通过。文件无法读取或检查不通过时，系统会阻断规划，不会把它当成空计划。 | 返回 `confirmed_baseline_invalid` 并阻断；需要先修复正式任务计划。 |
| 规划身份和冻结输入完整 | 工作流运行、线程和所属会话身份必须齐全。系统根据当前 TechnicalPlan 和工作区快照建立任务图基础结构（代码字段 `unit_skeleton`，列出职责分组及其依赖关系）；该结构必须包含当前范围要求的每个职责分组。复用事实必须准确覆盖正式基线任务；构建上下文（`build_context`）的范围须与显式目标一致，`FrozenContractStore` 中的 TechnicalPlan 正文须与规划正式输入一致，接口来源身份须可绑定。工作区快照、范围和正式基线摘要会作为本轮冻结输入。 | 在模型调用前失败；属于身份、输入或平台合同问题，不是模型生成质量问题。 |

#### 8.1.2 当前阶段报错的主要原因

| 表现 | 根因与处理方向 |
| --- | --- |
| 缺少正式文件、状态不是已确认，或上游摘要不匹配 | 生成适配器只读取当前工作区正式产物。检查相应 `.json` 文件的确认状态、`basedOn` 摘要及直接上游文件；需要时在对应正式产物流程中修正并重新确认。 |
| 正式 `build-task-plan.json` 存在，但报告 `confirmed_baseline_invalid` | 文件格式、读取权限、确认状态、`build-dag.v4` 结构或任务图校验不符合基线合同。不要把它当成首次规划的空基线；先修复正式计划，再重新发起规划。 |
| 页面/接口目标停在 API 设计前置门禁 | 当前目标关联的接口设计未完成、已失效，或门禁动作与原目标/接口合同不一致。完成相应字段映射后，显式重新检测；不能用 `EntitySourceBinding` 或旧工作流检查点代替当前接口设计。 |
| `TemplateState` 或授权能力报错 | 核对 `.devagentstudio/template-state.json`、`.devagentstudio/application.json` 和当前目标所需模板能力。应用配置开启授权而模板有效能力缺少 `authorization` 时，生成会被阻断。 |
| 在生成前出现职责、复用或冻结合同错误 | 常见代码问题包括当前范围引用了骨架外职责、正式任务归属不完整/冲突，或 `FrozenContractStore` 的来源身份与正式接口设计不一致。查看结构化 `code`、职责分组和来源身份；不要通过重试模型掩盖输入问题。 |
| 生成准备缺少工作区或会话身份 | 检查当前工作流是否绑定有效工作区、`owner_session_id`、`active_run_id` 和 `active_thread_id`。这些身份用于归属本轮 `PlanningRun` 和待确认任务计划。 |

### 8.2 任务生成阶段

`PlanningRun` 创建后报错，关键的诊断文件是 `.devagentstudio/plans/planning-run.json`。它是当前运行的轻量进度投影，不含候选任务正文，也不能用来恢复执行。遇到报错，可以先看顶层 `failure.code`、`failure.message` 和 `failure.details`；再看对应 `unit_states` 中的 `generation_status`、`attempt_in_round`、`current_issues`，以及顶层 `global_issues` 和 `global_repair_round`。`attempt_in_round` 只统计模型调用，不能单独用来判断确定性处理是否执行。

当发生职责计算或 `FrozenContractStore` 初始化在创建 `PlanningRun` 前失败时，该文件可能不存在；此时应检查工作流错误和后端诊断，不能把文件缺失当作没有错误。

模型基础设施错误还应查看 `failure.details.stage`、`http_status`、`provider_error_code`（若存在）。

#### 8.2.1 职责分组（Unit）校验规则

1. **先从当前范围计算新增职责，不按任务数量猜测。** `required_unit_ids` 必须是当前骨架里的明确身份。具体职责由已确认 TechnicalPlan、当前接口设计和目标范围推导；接口的物理数据源类型来自对应接口设计。未定义的职责身份、缺少骨架节点或正式来源冲突会在生成前失败。
2. **复用只认正式事实。** 系统按精确能力标识（`capability`）和正式接口实现归属判断职责是否已满足，不按任务标题、数量或执行状态猜测。没有新增职责时不调度生成；已有事实满足全部职责时只复用；仍有未满足职责时才产生新的候选任务。结构节点和模板前置能力不调用模型，权限资源职责由平台确定性处理。
3. **候选任务必须符合固定结构和归属。** 候选任务需具备规定字段，且 `unit_id`、`owner`、`task_type` 与冻结职责上下文一致；初始状态必须是 `pending`。`target_files` 必须与 `change_scope` 中声明的路径集合一致；路径须是安全的仓库相对路径，并且每个目标路径都必须属于 `allowed_paths` 允许的范围。交付物引用的路径也必须落在任务的目标范围内；候选不得输出平台拥有的字段、任务、修复或验证职责。
4. **单组依赖只允许引用授权目标。** 任务依赖可以指向当前候选任务，或同一职责分组的正式保留任务；不能引用未知任务、职责分组 ID 或其他职责分组的任务。跨组任务依赖会被单Unit内部校验报告为错误；任务编译器再依据职责分组依赖图生成平台认可的依赖。单组内部自依赖和循环依赖在单Unit内部校验阶段发现。
5. **所有需生成的职责分组都必须有有效候选才能组装。** `Generation Barrier` 只表示所有计划生成的职责分组都已结束当前轮次；如果其中有分组达到 `round_exhausted`，完整性检查会把它标记为缺失候选。缺失候选可能由全局修复重新生成，修复额度用尽或问题不可修复时才会使 PlanningRun 失败；其余分组的部分结果不能直接写成待确认计划。

#### 8.2.2 DAG 全局的校验规则

1. **只组装正式保留任务和本轮有效候选任务。** 组装是追加式的：保留当前正式基线任务、加入本轮候选任务，再由 `compile_build_task_plan_scope` 重新编译整图。不自动覆盖旧任务、合并重复 ID 或替模型改名。
2. **校验完整来源和编译结果。** 系统核对候选完整性、任务 ID 与职责归属、正式保留任务来源、接口实现归属，并重新计算任务依赖、业务交付物/契约约束、能力依赖和拓扑顺序。最终图必须通过校验、处于 `ready`，且执行批次中没有 `blocked` 项，才算全局通过。
3. **仅对可安全归因的问题重开生成。** 全局问题必须由确定性校验规则以结构化校验问题给出，并能依据任务来源和候选归属精确定位责任职责分组。重复任务 ID、接口实现归属冲突、依赖环、跨组关系或合同问题，并不意味着一律可以自动修复；若问题涉及正式保留任务、平台输入、归因矛盾，或有任一问题不可重试，系统不会挑出可重试子集继续生成。
4. **全局修复有固定上限。** 只有完整问题集合都可重试且目标明确时，才按目标职责分组重新生成；初次全局检查后最多再开启 2 轮全局修复。超过上限或出现不可归因问题时，PlanningRun 失败并保留完整诊断。
5. **全局通过才写入待确认计划。** 通过后进入 `persisting_pending`，系统原子写入 `.devagentstudio/drafts/plans/build-task-plan.pending.json`，并绑定 `DraftIdentity`、基线摘要、输入指纹和目标范围。正式任务计划此时仍未更新。

#### 8.2.3 当前阶段报错的主要原因

| 错误类别 | 典型原因 | 自动处理边界和定位方向 |
| --- | --- | --- |
| 候选内容或单Unit内部校验 | 空/截断/无法解析的模型输出；缺少必填字段；任务职责、`owner`、状态或交付物不符；路径超出允许范围；依赖目标无效或单组内成环。 | 可修复的内容问题会连同最近一次错误反馈给该组；每轮最多 3 次模型调用（含首次调用）。如果仍无有效候选，完整性检查会把该组列为缺失候选，并可进入最多 2 轮全局修复。查看该组的 `current_issues` 和 `attempt_in_round`；这不是 Build 执行失败。 |
| 模型基础设施故障 | 模型配置/客户端初始化、请求调用或整个职责分组会话超时失败。 | 生产策略将 SDK `max_retries` 配为 `2`；只有 SDK 判定可重试的请求错误才会按策略重试。这与单组内容尝试分开计数，也不会从已中断的流式响应位置续读。最终基础设施错误以 `category=infrastructure` 终止当前 `PlanningRun`，不进入单组或全局内容重试。结合 `stage`、HTTP 状态和服务提供方错误码检查配置、网络及服务端状态。 |
| 冻结来源或平台合同错误 | `FrozenContractStore`/`FrozenContractReader` 来源损坏、候选身份与当前运行不匹配、进度快照写入或发布失败。 | 这些不是模型内容问题；通常会直接终止当前运行。根据错误中的来源引用、职责分组、运行身份和阶段检查正式合同、当前 `PlanningRun` 投影及工作区文件访问。 |
| 全局组装/校验 | 正式保留任务与候选任务 ID 冲突、同一接口存在多个正式实现归属、任务图成环、能力/契约约束不满足、执行批次被阻塞，或全局问题无法精确归因。 | 只在所有全局问题都可安全归因时，平台才重试对应职责分组，且最多 2 轮。正式保留任务冲突、平台输入错误、无法归因或混有不可重试问题时会整体失败；检查 `global_issues` 中的 `code`、`task_ids`、`retry_unit_ids` 和任务来源。 |
| 状态/文件持久化 | 写入 `planning-run.json` 或原子写入待确认任务计划时发生文件权限、路径、磁盘或状态身份错误；待确认计划的来源、摘要、范围或自摘要校验失败。 | 没有合法的 Pending 文件和确认身份，就不会展示可确认的结果。检查后端异常及对应文件路径/权限；不要通过手工创建或修改 Pending 绕过 `DraftIdentity` 与校验。 |

### 8.3 任务确认阶段

确认阶段不是“收到确认动作就直接提升文件”。确认请求的 `planning_run_id` 和 `draft_digest` 必须匹配当前 Pending 的身份和自摘要；如果同一计划已经正式确认，重复动作会按幂等结果处理；已放弃的草稿不能再次确认。通过身份检查后，服务端重新读取正式基线和当前正式输入，比较基线摘要、完整输入指纹与目标范围，并重新校验 `build-dag.v4`、模板上下文、任务图和执行批次。

- **确认**：身份过期、正式基线变化、当前正式输入变化或计划复核失败时，分别可能返回 `stale_draft`、`stale_base`、`stale_inputs` 或 `invalid_dag`，不会提升正式计划。全部通过后才原子写入 `.devagentstudio/plans/build-task-plan.json`，再清理匹配的待确认计划。
- **放弃**：只删除身份和摘要匹配的当前待确认计划，并结束对应 PlanningRun；不会修改正式任务计划。身份不匹配或待确认文件自摘要无效时，拒绝把另一个草稿当作本次放弃目标。
- **重新生成**：先验证旧草稿身份并消费旧待确认计划，再重新读取当前正式任务计划和其它正式输入，创建新的 `PlanningRun`。旧待确认计划被消费后，输入重建、模型生成或新待确认计划写入任一步失败，都不会恢复旧草稿；新的结果仍须重新确认。

### 8.4 排障时区分的问题类型

| 观察 | 更稳妥的解释 |
| --- | --- |
| 单组尝试次数用完 | 某个职责分组的候选任务连续没有通过单组检查；查看该组每次生成的错误。 |
| 模型调用环境故障 | 错误发生在初始化模型或请求模型时；再查模型服务可用性、权限、限流、网络、超时和模型配置。仅凭错误标签无法认定根因。 |
| 接口契约或输入产物无效 | 节点读取的正式产物、只读接口契约或已固定的输入不可靠；这不是“模型写错任务格式”。 |
| 全局修复停止 | 全局任务图的问题无法明确归到职责分组，或两轮修复次数已用完；查看问题列表和被标记为可重生成的分组。 |
| 前端没有显示可确认任务 | 先检查待确认任务计划的候选来源记录和草稿身份；缺少或无法验证时，系统应要求重新生成，不应由界面猜测要展示哪些任务。 |

## 10. 多数据源能力分析与待决策场景

### 10.1 结论速览

这里要区分两种“多个”：**数据源类别**是数据库或外部 API 这类类型；**数据源实例**是某个具体数据库 ID、数据库连接，或某个具体 API 地址（服务根地址）。例如两个不同数据库仍属于 `database`（数据库）类别，但属于两个实例。

**已知事实**

- 职责计算会查看已确认接口设计中“每个字段来自哪里”的映射、数据库读写规则和外部 API 绑定，并把它们归为 `database`（数据库）、`external_api`（外部 API）或 `static`（静态数据）类别。
- 代码函数 `endpoint_source_types` 只返回来源类别，不返回“每个具体数据源一条”的清单。`backend:bootstrap` 按 `database`、`external_api` 类别各建立至多一条共享职责，不按每个数据库 ID 或 API 地址单独建分组。`static` 对应前端静态数据职责，不属于后端初始化。
- 每个接口操作的实现分组及旧任务复用判断，都按正式接口定义编号和具体操作编号绑定。
- 接口设计既有单个 `sourceBinding`（默认数据源）字段；`fieldMappings` 和 `sourceFields` 记录各字段的数据来源，`externalApiBindings` 列出外部 API 绑定。因此，不能只凭 `sourceBinding` 是单字段就判断整个接口设计只能使用一个数据源。
- 自动化覆盖了一个接口操作同时出现 `database` 和 `external_api` 两类职责；没有从该测试推导多实例配置正确性。

**合理推断**

目前只读 API 资料和模型输入可能包含多个具体数据源引用；但生成职责会把来源归并到“数据库”或“外部 API”类别。**推断**：这能支持按类别生成一组后端工作，不能据此确认每个具体数据库或 API 地址都有单独的连接配置、初始化、权限或重试策略。

**建议**

建议先确认每个具体数据源如何命名、连接配置和密钥从哪里读取，以及多个 API 操作如何共享连接。之后再决定：仍使用一个后端初始化分组并维护明确的数据源清单，还是为每个数据源实例增加独立职责分组。不能只看生成代码“看起来合理”就宣称多个具体数据源实例都已正确支持。

### 10.2 场景矩阵

| 场景 | 当前证据 | 暂不能下的结论 |
| --- | --- | --- |
| 一个数据库 + 一个外部 API | 自动测试检查同一 API 操作会得到数据库访问和外部调用职责；提示规则中的任务清单要求业务服务依赖这两条分支。测试没有调用模型，也没有验证最终生成的任务图。 | 不证明模型每次都按清单生成任务，也不证明 Build 执行结果；此外，测试不覆盖数据库或外部地址的登录凭据、连接生命周期，或一个来源出错时对另一个来源的影响。 |
| 多个数据库 | 会汇总为 `database`（数据库）类别；具体数据源引用可能仍在接口资料中。 | 未证明每个库的连接和事务如何区分、是否会重复初始化，以及接口操作如何对应到具体数据库。 |
| 多个外部 API 地址 | 会汇总为 `external_api`（外部 API）类别；接口设计可以列出多个外部调用地址。 | 未证明每个地址都有独立调用客户端、认证、限流/重试规则和操作分发。 |
| 多个 API 操作共用同一数据源 | 各 API 操作仍有各自的实现分组，但同类别的初始化工作可以共享。 | 未证明共享初始化不会重复执行，也未证明不同操作使用不同数据源时的冲突规则。 |

### 10.3 建议补足的验证事实

若要宣称“多个具体数据库/地址都能正确配置和使用”，至少需要测试并记录：

1. 一个接口操作绑定两个不同的数据库数据源编号，验证生成计划是否保留这两个编号，并分别配置连接。
2. 一个接口操作绑定两个不同的外部 API 数据源及各自的数据源编号和服务根地址，验证是否分别生成调用配置并把操作发往正确地址。
3. 一个接口操作混合两个数据库和一个外部 API，验证任务依赖如何分支，并在业务服务处汇合。
4. 多个 API 操作共用一个数据源、以及各自绑定不同数据源，检查初始化是否重复、每项实现归属是否正确。
5. 在沿用旧任务、用户重生成和整图修复时，验证具体数据源 ID 不丢失、不错误共用；来源资料缺失时拒绝复用。
6. 检查密钥只从正式应用配置或密钥管理设施读取，不由模型生成或写进任务文本；检查日志、候选结果和进度显示不会泄露密钥。

这些是建议的验证场景，不是对当前实现的缺陷断言。
