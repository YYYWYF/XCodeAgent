# 工作台原型领域规则

本文档描述 `prototype/` 演示工程当前采用的工作台状态、对话关系、初始化规划、正式产物审阅、Workflow 边界和测试准备规则。它是改版后原型的统一规则，不作为正式工程已经实现的架构声明。

## 一、本次重构结论

### 数据来源与绑定映射（2026-09-11）

- 左侧窄功能栏「数据来源」打开与任务管理同层级、同宽度的互斥抽屉，交互与任务管理抽屉完全同构：顶部复用同一套 Tab 栏按「数据库 / 外部 API」分页（下划线选中态 + 数量角标，右侧挂新增按钮），列表行只展示名称与接入标签，不做目录 + 详情双栏；数据库行内不展示连接字符串，直连行带“密码已配置/缺少密码”标签（对齐原工程）。
- 编辑弹窗复刻原工程数据库连接表单：连接模式三选一（内置数据库 / DBID / 本地直连），非内置模式填写 数据库地址、端口、Schema、用户名，DBID 模式追加 DBID 字段、直连模式追加密码（留空保持不变），新建内置模式提示无需外部连接信息；编辑已有连接时连接模式锁定不可改（改模式会让已填参数失效），连接明细仍可修改，并就地提示“连接模式在创建后不可更改”；外部 API 弹窗只维护 名称 + 域名/Base URL。表、接口、字段候选由实体开发时按需发现。删除有二次确认，外部 API 提示级联删除的目录与接口规模；直连提供模拟“检测连接”。目录通过 `aistudio:prototype:data-sources:v4` 浏览器缓存跨面板同步（结构升级即换键弃旧缓存）。弹窗浮层 Portal 到 body，主题变量经 `global.less` 的 `body:has(...)` 桥接（`.wb-light-tokens`），否则 `--wb-*` 解析不到会渲染出透明弹框。
- 实体的实现结构升级为“计划意向 → 开发绑定”两段：计划阶段在技术规划方案“实体”子 Tab 中为每个操作记录实现类型与来源级意向（不选表/接口、不做字段映射）；开发阶段在“开发产物 → 实体 → 方法”中完成表级/接口级绑定，保存后 AI 自动推导字段映射（能确定的自动填充，疑似歧义的字段置为待确认），用户逐个确认歧义字段后“确认绑定”。意向阶段没有确认门，绑定确认以“全部字段已匹配”为前置条件。开发产物目录不设文件夹级：实体直接罗列（BlockOutlined 图标），展开下一级即方法清单（统一术语「方法」，内置方法用锁形图标表达平台锁定模板、需求自定义用函数 ƒ 图标；点实体行 = 选中并切换方法清单展开态；新增入口收在实体行尾悬停显现的省略号下拉菜单里——行内兄弟节点而非浮层，悬停时替换状态圆点；删除方法在工作台方法头部且仅自定义可删）；右侧由目录选择驱动，两页各司其职，且**面板只读呈现设计定稿、不在面板内编辑**：**实体页（字段维护）**头部是只读数据来源卡——展示已确认的类别标签（数据库/外部 API/混合）与库表绑定行，数据库类别附实体字段↔表字段对应表（同义自动对应、疑似与无关标待确认），并注明内置增删查改方法由平台按表结构模板生成；底部注明“绑定在实体开发工作流中确认，需要调整时在对话中重新发起”。**方法页（方法定义）**呈现出入参契约（操作输入/返回字段/页面使用以 chip 结构化展示）+ 数据实现与字段绑定工作台（ImplementationPanel：实现类型→绑定目标→AI 自动匹配→逐字段确认→确认绑定门）。数据来源类别模型：纯 DB 单表走模板内置方法，纯外部 API 按业务自定义方法逐个绑定固定契约（出参翻译 + 入参适配），混合/多表联查走高级自定义（SQL/Java 编排）；对象来源的“对话交互卡片式调整工作流”与入参槽位结构化适配为下一步。

- 需求描述沿用现有需求表单、AG-UI 保存草稿和需求文档确认流程。计划阶段的数据实现为交互草稿；不读写真实数据库、不调用外部服务、不写回 TechnicalPlan，也不替代原 Workflow 的产物确认门。原型通过 `aistudio:prototype:*` 浏览器缓存让实体的数据实现从计划阶段延续到开发阶段，演示辅助的“清理演示数据”会一并复位。正式落地时必须接入既有 AG-UI 产物与确认流程，不能把本机缓存作为生产存储契约。
- 组件职责：`BusinessObjectsPanel` 负责阶段投影与草稿；`BusinessObjectEditor` 负责局部编辑；`OperationDetails` 负责操作与页面关系；`ImplementationPanel` 负责来源选择、AI 匹配、异常处理与确认（2026-09-11 起拆分为“计划意向 / 开发绑定”两种模式）；`DataSourcesPage` 只管理数据库和外部服务目录，不承担绑定。来源目录与实体草稿分别由 `DataSources/catalog.ts`、`BusinessObjects/store.ts` 跨面板同步。样式复用浅色/深色 `--wb-*` 主题变量，并适配窄右侧面板。
- 技术规划方案的用户投影对齐原工程 DocPanel 的五段结构，二级页签为「架构 / 实体 / API 契约 / 页面 / 权限」：架构承载三层技术架构与数据来源目录；实体沿用 TechnicalBusinessObjectsReview（实体投影）；「API 契约」由实体操作实时投影为 REST 资源契约（每对象一个复数资源、每操作一个接口，方法按操作语义映射、内置 CRUD 走模板路径、自定义动作取演示短 id），接口行可点开 Inspector（鉴权/参数/请求/响应/错误码/数据实现意向），页签内交互只改阅读位置；「页面」逐页展示 `页面 → 实体.操作() → METHOD path` 绑定行；「权限」把 requirementSpec.user_roles 投影为角色卡，权限去“查看/查询”前缀后与操作名双向包含匹配到接口，未命中标注“待开发阶段绑定”。审阅面板排版同步收敛：章节标题 20/12px 纵向节奏、卡片 14/16 内距、技术规划方案专属样式拆分到 TechnicalPlanReview.less。底层演示 JSON 仍保留 Endpoint/API Contract 作为内部结构；开发产物目录同样隐藏独立接口分组，用户点击实体后直接在右侧选择操作并绑定数据库或外部服务。
- 原型验证使用 `pnpm typecheck` 和 `vite build --config vite.prototype.config.ts`；`prototype/` 没有 `build` 脚本。验证输出目录 `dist-business-objects/` 已忽略。

本次改版用以下五条新规则替代旧原型规则：

1. **对话不再拥有产物编辑权。** 产物和代码文件由活动 Workflow 的 DAG/Task 范围临时控制写入；对话只负责用户交互、任务发起和状态呈现。
2. **对话严格隶属于阶段，阶段间消息、Workflow 与推进权完全隔离。** 需求分析、项目计划、开发、测试、审查和验收各自有一条默认常规对话；“默认单对话”仅指用户可在当前阶段不拆分上下文地完成该阶段旅程。页面、接口等上下文显著增多时，专业开发者才在当前阶段主动新建常规对话隔离上下文。每个阶段同一时刻只有一条“当前推进对话”。当前推进对话有运行中或待确认任务时禁止新建；空闲时点击“新建”即创建并直接取得推进权，可以马上输入。点击已有对话只切换查看对象，不转移推进权；查看非推进对话时，用户可从顶部提示主动发起并二次确认转移。打开、新建或查看对话不联动产物选择、右侧文件/预览、弹框或其它视图。
3. **业务测试用例提前异步准备。** 需求规格说明书确认后，用户先选择“异步任务”或“潮汐任务”，用例队列整体进入对应任务系统；开发期间持续生成，顶部测试阶段的数量芯片动态绑定用例所在队列并可直接打开该系统抽屉，右侧“测试用例”Tab展示详情。开发完成即可进入测试，单条用例只有在生成并校验后才可执行。
4. **开发阶段代码实现通道化。** 前台 Workflow 的用户产物只分为页面与实体。页面开发负责布局、交互与调用 `实体.操作()`；实体开发负责逐操作绑定数据库/外部服务、AI 字段匹配、多来源关系与数据处理逻辑。内部 Endpoint 可继续作为实现结构存在，但不进入用户产物清单、发起器或开发计数。

5. **初始化规划与工作台状态分离。** 设计阶段只审阅一份需求规格说明书；页面行为、状态和验收以表单字段合并进该说明书，ProductPlan 仅保留为下游生成的内部结构。计划阶段独立审阅 TechnicalPlan，确认后才生成模板并进入开发；设计与规划文档均不再走 Diff。初始化规划记录按应用版本持久化在浏览器缓存，状态转换由领域状态机校验，剧本只负责模拟进度和 AG-UI 快照；演示辅助悬浮球（`show-helper/`，位于 prototype 根目录、与 mock-data 同级的原型辅助区，不属于正式渲染层代码，经 @show-helper 别名挂载）常驻悬浮于界面右下角，可拖拽挪位、点击展开功能菜单，其“清理演示数据”只清理原型缓存（会话、任务与初始化状态），不删除静态存量应用目录。
6. **设计与规划确认均由对话主导，右侧原位编辑。** "确认需求规格说明书""确认 UI 设计稿""进入技术规划方案""重新生成 / 确认技术规划方案"都是各自 Workflow 节点内的连续动作；右侧仅在"预览"和"编辑"两种本机状态之间切换，不使用弹窗或右侧确认按钮。**"修改需求"与右侧面板头部的"编辑"开关只是把右侧切到原位表单的本机动作，不作为工作流答案提交、不消耗确认门**；确认卡保持挂起，用户保存草稿或退出编辑后仍在原卡确认或继续调整。**头部右侧只放两组控件：状态切换开关（预览|编辑，锚定右缘不位移）与保存草稿（仅编辑态出现在开关左侧）**；状态标签（待确认/编辑中/已确认）固定在左侧标题区，不参与右侧操作区的增减。**编辑态与预览态共用同一组分栏（概览、页面与操作、业务流程、实体、权限需求、验收标准），激活分栏在两种状态间保持，观感上是同一份文档**；页面基础信息与页面行为、状态、页面验收合并在"页面与操作"分栏内维护。**UI 设计稿首次生成期间右侧保持需求规格说明书预览（标记已确认），生成完成进入逐页确认时才切到 UI 设计稿；确认阶段内的重新生成（批量选模板）期间右侧停留当前产物不切换**；原位表单编辑期间右侧不自动切换产物，避免丢失编辑中的草稿。活跃门禁卡所在的轨迹节点保持展开，下一步入口不能被节点收起折叠。需求确认前按真实 RequirementSpec 的应用定位、角色、模块、页面、实体、流程、权限、页面行为和验收标准执行完整性检查，生成提示词同步进入原型 AG-UI 状态。右侧自动跟随按“产物里程碑”让位：同一产物审阅期间用户手动切换 Tab 后不抢回；下一个产物就绪待审阅（需求规格说明书 → UI 设计稿 → 技术规划方案）时右侧重新接管并定位到当前门禁产物。任何规划确认、重生成或阶段进入提交成功后立即退出右侧原位编辑态（过程互动静默操作除外）——编辑草稿基于旧版本，不允许继续保存。确认卡进入编辑的按钮与右侧开关统一措辞为“编辑需求”；技术规划方案确认卡的“重新生成”先展开选填修改意见输入，留空才退回默认文案。

旧版以下规则已经废止：

- “一个产物只能由其默认对话编辑”；
- “系统按产物自动创建产物专属对话，并自动投放模板卡推动工作流”（现在的多条开发对话由用户按边界主动创建，产物由用户 @ 提及发起）；
- “点击产物必须跳回所属对话”；
- “静态依赖或输入框附件用于扩张对话写权”；
- “测试阶段只有一份测试报告，不展示用例清单”；
- “普通新建对话可以承接正式代码修改”。

## 二、核心层级

**应用**：用户持续维护和迭代的软件工程，是版本链的根。

**版本**：一次完整制作周期形成的不可变资产快照。版本生成后，当前版本的产物、Workflow 操作和对话输入只读；新变更只能发生在后续迭代版本。

**阶段**：单个版本依次经过设计、计划、开发、测试、审查和验收。设计阶段包含需求规格说明书确认与 UI 设计；计划阶段包含 TechnicalPlan 与模板生成。版本生成是验收后的确定性终态动作，不是第七阶段。

**阶段主对话**：当前阶段的默认正式交互入口。用户可以一直在主对话推进，也可以主动新建额外对话隔离上下文；对话数量不由产物数量决定。它可以先后启动多条 Workflow，汇总阶段状态并引导用户满足准入条件，但它本身不拥有文件或产物写锁。

**Workflow 实例**：一次具有明确目标、DAG、任务范围和终态的正式执行。一个阶段主对话可以承载多条 Workflow；一条 Workflow 可以交付多个强关联产物，并在 DAG 内并行执行路径不冲突的任务。

**产物**：工作区中的长期业务事实。设计阶段产出一份需求规格说明书与可选 UI Manifest；页面行为的内部结构随说明书保存，计划阶段产出 TechnicalPlan 与模板就绪事实，开发阶段交付页面/接口/实体及代码，测试阶段执行测试用例并记录结果与缺陷，审查阶段交付审查报告，验收阶段不新增正式文档。

**代码文件**：实现一个或多个产物的工程事实。文件不属于阶段主对话；每次修改必须归属于当前 Workflow 的具体任务和允许路径。

## 三、对话、Workflow 与产物关系

关系固定为：

```text
一条阶段对话 → 多条 Workflow
一条 Workflow → 一个或多个相关产物
一个产物 → 历史上可被多条 Workflow 依次修改
一个产物在同一时刻 → 只允许一条活动 Workflow 写入
```

每个阶段默认使用自己的主对话，用户需要隔离上下文时才在该阶段新建额外常规对话；开发阶段通常最需要拆分，但对话管理规则对其它阶段保持一致。进入下一阶段时，系统创建或恢复下一阶段的默认对话，不能复用上游消息、Workflow 或编辑权限。开发阶段右侧默认打开“开发产物”Tab；进入编码 Diff 时临时切到“应用文件”，产物审查仍回到“开发产物”内容区，不使用独立浏览器。编辑权限是独立于产物、且以阶段为边界的单一权限，只有用户明确确认后才在当前阶段转移。

产物上下文和文件范围由当前 Workflow 根据正式计划、DAG、目标文件和允许路径确定；对话不维护产物附件、归属或写锁。

## 四、阶段与主对话职责

### 1. 设计阶段 · 产品 Agent

设计阶段主对话澄清业务目标、角色、流程和功能边界，随后生成一份需求规格说明书；用户通过与真实工程对齐的表单维护应用、页面、角色、页面行为、状态、权限和验收标准，确认后才生成 UI 设计稿。UI 设计稿按页面独立展示（顶部页签横排，与本面板其它产物的分栏方式一致）；「确认 UI 设计稿」卡内逐页列出待选版式（未选择前显示“待选择版式”，不展示种子默认模板名）并可展开“选模板”（低保真线框翻看候选，翻看起点定位该页当前版式）；选模板只本地记录不触发生成，全部页面选定后自动一次性批量交后台重画、右侧预览统一刷新；生成中卡片钉住、只加“生成中”标签并禁用动作；生成完成后“确认全部设计稿”才可点击；确认或跳过后卡片转为终态记录——逐页模板名 + 已确认标记，不再渲染动作按钮。右侧 UI 设计稿面板为纯静态呈现（页签、预览、页签上的已确认对勾），不提供任何第二套确认/重画入口。确认或明确跳过后阶段完成：产品 Agent 只输出一句收尾文本（不再渲染阶段门禁大卡），进入计划阶段由统一的 PhaseGateModal 弹框承载——弹框自动弹出一次，可「暂不进入」，之后从顶部阶段条「计划阶段」再次唤起，确认后才生成技术规划方案。正式文档不展示 Diff。

**一问一答与单卡单消息。** 设计/计划阶段对话对齐原工程：不是工作流轨迹驱动，而是一轮对话一条消息，每条 assistant 消息至多直接挂一张交互卡（澄清向导卡或确认卡），不渲染 ProcessSteps，也没有外层汇总壳卡。生成中的轮次展示轻量进度条（“正在生成需求文档 / UI 设计稿 / 技术规划方案…”）；用户在卡片上提交澄清或确认后，答案先以用户消息留痕（澄清/修改意见提交只补一句确认话术，答案由上方转为只读回看的卡片承载，不重复罗列；确认/重生成/阶段进入为一句用户口吻指令，技术规划方案重新生成携带真实修改意见），随后追加一条新的 assistant 消息——对话呈现一轮一轮来回的节奏；上一轮的卡片留在原消息里禁用只读回看。右侧保存草稿等静默续跑只刷新当前消息的快照，不新增对话轮次、不产生用户消息；UI 设计稿确认阶段的过程互动（批量选模板）同样静默续跑——原地刷新当前确认卡与右侧预览，整个确认阶段自始至终只有一张活动卡，直到“确认全部设计稿”或“跳过”；改稿轮生成期间快照短暂不带 clarification，卡片按 ui_confirmation 阶段名兜底钉住（MessageList 与卡片双重判断），绝不卸载重挂——只把动作按钮置为禁用并显示“生成中”状态标签，右侧面板布局恒定、生成状态只出现在预览区；“确认全部设计稿”在所有页面完成版式选择并生成前保持禁用；确认/跳过提交后追加的新 assistant 消息只有一句阶段收尾文本，`planning_stage_entry` 门禁与 `development_entry_confirmation` 一样不在对话区渲染卡片（WorkflowRunCard 返回 null），由 PhaseGateModal 统一弹框承载并支持顶部阶段条再唤起；开发/测试阶段的原地确认（Diff 接受、验收、执行方式选择、用例授权）同样不插用户消息。确认卡不展示「已生成产物」落库路径分区——产物本体由右侧审阅区承载，路径属于内部实现细节（ProductPlan 等内部结构更不得作为用户产物露出）。

**确认卡历史。** 用户提交澄清或确认后，原消息中的确认卡必须保留问题、选项和提交答案。历史卡保持原有向导形态与“第 X / Y 项”步骤指示，通过“上一步 / 下一步”翻页回看每一题的当时选择；控件整体禁用置灰、不再提供提交动作。历史卡不能只显示“已失效”的空提示，也不能把多题平铺成静态长表单。

**产物发起引导卡。** 空开发对话与无目标发送由研发 Agent 投放一次「产物」发起引导；引导消息复用对话区交互卡的卡壳（workflow-run-card：同一套背景、圆角、内距与信号点标题结构），只是卡内内容不同——分“页面 / 实体”两个浅色分组区块（带与产物面板左列同款的类别图标）平铺全部候选产物。行内只保留名称与状态徽标（待实施 / 实施中 / 后台任务 / 已交付 / 继续处理），不展示路由、字段数等补充字段；路由等补充文本仅作为产物面板搜索的匹配数据，不进展示层。发起卡与输入区「产物」按钮共用同一份候选、状态徽标与发起链路：点击“待实施”行直接发起实施（不产生用户消息输入），点击“继续处理”行恢复该产物的后台工作流，禁用行保持静态置灰并以悬浮文案说明原因。旧的“一句话 + 选择产物链接”形态废止；输入区两级选择器保留，用于产物较多时的搜索定位。

### 2. 计划阶段 · 项目 Agent

计划阶段主对话读取已确认的需求规格说明书与 UI Manifest，生成 TechnicalPlan；TechnicalPlan 由开发角色审阅确认后，才进入应用模板生成与开发准入。技术规划方案承载架构、实体、API Contract、Schema、页面技术绑定与默认角色授权（权限页签投影需求角色），不重复维护产品行为。确认技术规划方案后模板生成是计划阶段最后一环：Agent 只补一句「技术规划方案已确认，应用模板已生成，计划阶段完成。」收尾文本，进入开发阶段由统一的开发准入门弹框（TestCaseTaskTypeModal，PhaseGateModal 壳，选择测试用例生成任务类型）承载——领域状态先落到新增的 `awaiting_development_entry` 门禁阶段（快照 mode=`development_entry_confirmation`），弹框可「暂不进入」，之后点击顶部阶段条「开发阶段」再次唤起（workbenchPhase 将该阶段归入计划阶段集合，旅程在确认前不推导进开发）；确认后记录任务类型、推进到 `ready_for_workbench`，自动切换到开发阶段对话并创建测试用例后台任务。

### 3. 开发阶段 · 研发 Agent

开发对话负责页面和实体实现，以及单元测试、调用检查、构建和基础启动验证。进入开发阶段不自动投放模板卡，研发 Agent 先提示用户从「产物」入口选择“页面 / 实体”。页面候选显示页面名与路由，实体候选显示字段数与操作数；二者共用待实施、实施中、后台任务、已交付和继续处理状态。选择页面后进入模板、布局与交互设计；选择实体后右侧直接打开对象工作台，主对话显示“读取实体结构 → 绑定操作的数据实现 → 生成数据适配逻辑”的轨迹。页面对内部接口无感，只调用已经确认的 `实体.操作()`。产物实施时右侧与生成过程配套展示：工作流「生成代码」节点按帧渐进产出 Diff，首个分帧到达即切到右侧源码区并逐帧跟随累计；生成结束落「确认代码变更」时源码区已是完整 Diff，撤销/接受授权仍只保留在对话区改动卡上。页面工作流只交付页面本体（选择页面模板 → 详细设计四步 → 选择页面执行方式 → 生成代码 → 确认代码变更 → 启动产物审查），不再包含「选择接口执行方式 / 接口代码生成」环节；页面数据通过 实体.操作() 提供，构建计划与页面详设数据也不再携带接口单元。

**多条常规任务。** 任务管理抽屉只列出当前阶段的常规任务，并提供“新建任务”。列表不展示消息数、待确认等业务状态，只标识唯一的“当前推进”任务；该任务执行工作流时显示“推进中”，其余任务默认即在行内显示“仅查看”，不依赖选中切换。所有条目同宽等高，用户自建任务的删除按钮常显收在条块右缘槽位内（二次确认，删除后聊天记录一并清除）；当前推进中的自建任务删除按钮置灰不可用（业务上不允许删除推进中的任务，悬浮提示先转移推进权，转移后即可删）；阶段默认任务是该阶段唯一的系统推进入口，不渲染删除入口。新建是明确的工作意图：当前推进任务有真正运行中或仍可操作的待确认事项时，“新建任务”置灰并提示先完成当前任务；阶段准入门（规划/开发）挂起不算未完成事项，不锁新建，且门禁检测跨该阶段全部会话进行，推进权切到新建任务后弹框与顶部入口仍可正常确认；确认一经提交、卡片转为历史记录，就必须立即释放运行占位，不能再阻止新建。空闲时新任务立即成为当前查看上下文并取得推进权，可以直接输入，同时不清空或切换右侧产物、文件、预览和弹框。点击已有任务只打开历史，不弹权限框，且任务管理抽屉保持打开——切换、删除、新建等管理动作连续进行不被打断，条目徽标与选中态随切换即时刷新；查看非推进任务时，原推进任务空闲才可从顶部提示二次确认转移推进权。空开发任务取得推进权后由研发 Agent 投放一次「产物」发起引导，只读期间不投放。开发者可以按自己的认知边界组织上下文，例如把两个相关页面放在一条开发任务中；任务不绑定产物归属，产物写入仍由活动 Workflow 承载。

两套任务系统从存储到调度完全独立：异步任务（常规算力域）与潮汐任务（闲时算力域）各有独立流水、独立入口与抽屉，引擎逐系统推进、互不等待，同一系统内一次只执行一个任务——用例生成与代码实现都在本系统队列里按顺序逐个推进。后台实现任务按“排队 → 执行 Build DAG → 生成代码 → 构建及单元检查 → 启动产物审查 → 完成”无人值守推进；同步任务由剧本在对话内按同一阶段顺序当场推进（生成代码后经「确认代码变更」接受 Diff，再经「启动产物审查」节点把右侧工作区切换到“开发产物”并定位当前产物），引擎不调度同步任务；其记录仅用于产物状态推导，不进入任何队列抽屉，验收入口由对话输入框的「待验收」快速选择承载。

工作流底层采用“一套 DAG、多种表现段”的模型（`mock/workflowGraphs.ts`）：真实工程的底层 DAG 庞大交织，对话面板只呈现本次选中执行的一段。开发工作流注册了一张完整 DAG（页面设计分支与接口设计分支交织，汇聚到“选择执行方式”，再分出同步构建链与后台构建链，完成后进入验收段并预留验收调整回流）；需求分析工作流与项目计划工作流也各自注册了完整 DAG（节点序列对齐真实工程应用规划 Graph 的 requirements / project_planning 段：澄清与确认都是待输入门禁；「需求变更意图分析」借自真实工程的 design_intent_analysis、「映射业务权限规则」借自真实工程 ProductPlan 的权限规则映射），剧本只负责从 DAG 选段播放——详细设计段、同步任务段、派发收口、需求澄清/文档段与产物验收段的节点标题均以 DAG 为唯一来源，因此不要求界面展示的节点一致，但同一种工作流的底层图是一套。验收段回主对话执行：先播放“打开产物审查”节点，再挂“确认验收”待输入节点，确认后节点收口。任务完成即落“已完成”终态；完成后的后续步骤（如产物验收）以入口形式挂在任务条目上，点击在阶段主对话启动对应工作流——验收工作流打开右侧预览并承载确认，确认后产物标记完成、测试依赖解除。任务中心和产物状态是权威入口，完成通知不向对话末尾插入迟到的 Assistant 消息。

开发对象分别维护“未设计 → 设计中/实现排队/实现中/待验收 → 已完成/失败”状态。所有当前开发对象完成（验收通过）并通过开发门禁后即可进入测试阶段；尚未生成的测试用例在测试用例工作台中置灰，直到准备完成。

### 4. 测试阶段 · 测试 Agent

测试主对话从完整应用视角执行已经确认的业务测试用例。测试阶段先运行“非功测试工作流”（启动测试、非功能检查等少量节点），该工作流不选择或改变任何业务用例状态。随后按目录顺序为每条业务用例创建一条“用例测试工作流”。授权卡出现即表示当前用例 Workflow 已启动，目录将对应的单条用例标为紫色进行中；卡片只负责让用户确认是否执行这一条用例。确认后依次执行测试脚本、生成缺陷清单；有缺陷时继续调度返修节点并完成回归测试，无缺陷时直接结束当前 Workflow。当前用例的缺陷、修复状态和执行证据同步显示在右侧详情中。Workflow 完成且缺陷全部关闭后，该用例才标为绿色完成并进入下一条；尚未开始的用例始终保持灰色。用例执行本身不调用模型；执行器按依赖和运行资源进行有界并发，并记录证据。

失败用例生成结构化缺陷，关联用例、证据、受影响开发产物和代码 revision。缺陷修复作为用例测试 DAG 中的返修节点被调度，修复后必须执行对应回归节点；全部必需用例取得终态且阻塞缺陷关闭后，才允许进入审查阶段。

### 5. 审查阶段 · 审查 Agent

审查主对话只在测试门禁通过后进入，独立检查代码规范、安全、健康度、可维护性、计划一致性和交付完整性。审查 Agent 默认只读代码，只维护审查报告；审查问题通过开发主对话创建返修 Workflow。

### 6. 验收阶段 · 产品 Agent

验收主对话辅助用户依据需求文档和应用预览完成确认。验收阶段不新增正式文档；不通过意见由验收主对话判断是否属于当前基线，必要时进入新的需求迭代。

## 五、阶段二级对象清单与左侧导航

页面层级为：

```text
阶段主对话 → 当前阶段对象清单（按需出现） → 右侧文件/预览面板
```

- 设计阶段：右侧按 Tab 展示需求规格说明书和 UI 设计稿；页面行为与验收已合并在需求规格说明书内。
- 计划阶段：右侧展示 TechnicalPlan 的架构、实体、API 和页面绑定，并保留只读的「需求规格说明书」Tab，供审阅技术规划方案（实体、页面绑定）时对照需求来源。
- 开发阶段：展示页面、接口和实体清单及各自完成状态。
- 测试阶段：展示测试用例分组、执行状态和缺陷清单。
- 审查阶段：没有二级清单，右侧直接展示审查报告。
- 验收阶段：没有二级清单，右侧直接展示应用预览和验收动作。

二级清单只用于存在多个需要独立选择、执行或验收对象的阶段。它不是对话目录，也不提供“基于产物新建对话”操作。

二级清单属于阶段状态，不再长期占用左侧会话导航。基础原型的左侧固定为窄功能栏，上下两组：顶部是抽屉类入口「任务管理」和「后台任务」，一道横线收尾；用户功能入口「文件」「技能」「设置」与底部头像贴近、沉底成组。**「任务管理」是第一入口**：抽屉顶部是「常规任务 / 临时任务」固定 Tab 分栏（各带数量角标，默认选中常规任务，交互与异步/潮汐任务抽屉的 Tab 一致），下方单一列表平铺当前 Tab 的条目，条目内以“常规 / 临时”类型标签区分；两个 Tab 各有一行常显说明（位置与样式一致）——常规解释“当前推进”语义（仅当前推进的任务可执行工作流，其余任务仅供查看），临时解释能力边界（可用于讨论问答，无法执行工作流）。Tab 栏右侧「新建任务」按钮跟随当前 Tab——临时 Tab 下新建临时任务，当前推进任务未完成时按钮静态置灰并以提示说明原因。用户自建任务的删除按钮常显在条块右缘槽位内（各行同宽），删除需二次确认且不可恢复；阶段默认任务是唯一推进入口，不提供删除，运行中的任务同样不提供。常规任务支持自主新建、谨慎切换和唯一编辑权限；临时任务可以多开，只提供查阅、解释、分析和 Chat 类输入，不提供产物选择、Workflow、确认卡或写入能力。「后台任务」与顶部测试用例数量芯片是同一队列抽屉的两个入口；存在待验收实现任务时，入口悬浮文案直接给出“N 项待验收”。测试用例明细只通过该抽屉或右侧“测试用例”Tab查看，不在左侧功能栏重复放置入口。对象选择和 Workflow 进度均在中间主工作区或右侧工作台中呈现。

## 六、临时问答与任务管理

临时任务不再单设入口，被整合进左侧「任务管理」抽屉的“临时任务”过滤，并允许用户创建多条；初始不预置任何临时任务，切换到该过滤时列表为空，仅靠过滤标签下方的一行说明交代能力边界。它与常规任务共享管理入口，但保留明确的能力边界：负责代码解释、资料查阅、方案讨论和即时问题分析，不展示产物选择、Workflow、确认卡或写入工具，也不改变阶段、常规任务或产物状态。因为临时任务不占用正式编辑权限，所以即使某条常规任务正在运行或等待确认，用户仍可进入临时任务；这不会为其它常规任务解除输入锁。

如果用户在临时问答中提出修改要求，系统只形成结构化任务建议，并提示转到开发任务用 `@` 选择产物创建正式 Workflow。临时问答不会静默升级权限。

任务管理与临时问答共用统一辅助抽屉：

- 入口位于左侧窄功能栏第一项（「任务管理」）；
- 抽屉与后台任务队列抽屉完全同款同位：420px 面板从左侧菜单栏右侧滑出，头部为图标徽标、标题与一句话说明，不遮挡菜单栏、顶部栏与右侧面板；
- 各抽屉同一时间只能打开一个：打开任一个时自动关闭另一个；
- 抽屉覆盖主任务区域左侧，右侧文件/预览面板保持可见；
- 关闭后恢复主任务原位置和运行状态；
- 任务管理视图内可切换到「临时问答」视图，两者在同一抽屉内互切，临时消息历史保留；
- 临时任务可以多开，每条独立保存自己的受限 Chat 历史；
- 临时问答消息不进入阶段任务的 Workflow 上下文。

## 七、异步业务测试用例准备

### 1. 与单元测试的边界

异步生成的是业务场景、页面与接口组合路径、异常路径和数据校验用例，不替代开发阶段根据代码变更生成并执行的前后端单元测试。

### 2. 触发与执行

1. RequirementSpec 提供业务目标、角色、流程和验收标准。
2. 需求规格说明书带有预计测试用例概要（总量、业务场景和覆盖范围）；说明书确认后弹出任务类型选择，明确展示预计生成的用例总量。用户选择异步任务或潮汐任务后，后台创建独立测试用例准备任务，按业务模块和稳定场景分批调用模型。
3. TechnicalPlan 确认后，补齐页面、Endpoint、Schema 和实体绑定等可执行引用；能够确定性补齐的内容不重复调用模型。
4. 开发阶段正常推进，不等待后台生成完成。
5. 每批完成后立即校验并保存；单批失败只重试该批，不丢失其他结果。
6. 全部用例生成和校验完成后自动进入“已就绪”，不增加用户重复确认步骤。

后台状态为：

```text
排队中 → 生成中 → 校验中 → 已就绪
                    └→ 失败
上游正式产物变化 → 已失效 → 重新排队
```

用例集合绑定需求规格说明书、其内部页面行为和 TechnicalPlan 的当前 revision。上游正式产物修订后，受影响用例不得继续用于测试准入。

### 3. 顶部数量芯片、后台任务抽屉与测试用例工作台

顶部测试阶段只展示用例数量，不再显示“待确认”“已就绪”等状态文案，也不额外发送 Toast 或向阶段主对话重复插入通知：

```text
测试阶段 2/6
```

数量芯片是独立于阶段控制条的任务入口：它渲染在测试阶段按钮之外，即使阶段按钮因旅程未到达而禁用，芯片从计划确认起就始终可点击。悬停数量时提示“测试用例 2/6”；点击芯片动态绑定到用例任务实际所在的任务系统——开发准入门选定异步则打开“异步任务”抽屉，选定潮汐则打开“潮汐任务”抽屉，不触发阶段切换或进入确认。点击测试阶段本身或直接进入测试阶段，才会打开右侧“测试用例”Tab；测试阶段不提供浏览器 Tab。该 Tab 复刻开发产物的“目录 + 内容”布局：左侧只展示业务测试用例树，按场景分组并展示异步生成数量，右侧展示所选用例的前置条件、执行步骤、预期结果和本轮测试结果。

后台任务完成后带后续步骤（如产物验收）时有两类配套入口：任务抽屉条目上的「验收」按钮，以及开发主对话输入框工具栏的工作流入口（仅开发阶段对话提供，不随版本后台任务泄漏到分析/规划等阶段）——点开产物弹层后，待验收产物在自己的行上直接以「继续处理」徽标呈现（按钮化），点击即在主对话启动；工具栏图标保留紫色呼吸圆点提示存在待继续项，仅当开发阶段没有产物列表可承载时才退回独立的待继续列表兜底。两者复用同一条启动链路：定位产物 → 右侧打开产物审查 → 主对话播放验收段。同步任务在对话内确认代码变更后即交付完毕，不产生待验收，也不出现在该入口。

异步任务与潮汐任务从左侧菜单栏就拆成两个独立入口（沙漏/月亮图标；同步任务为闪电图标，仅出现在执行方式选择卡。图标语言：同步=闪电当场执行，异步=沙漏放后台慢慢跑，潮汐=闲时月亮；同步任务的验收入口在对话输入框，不在抽屉），各自滑出一个结构完全相同的队列抽屉：标题、头部徽标与入口共用同一套图标语言，从左侧菜单栏右侧滑出，不遮挡菜单栏、顶部栏与右侧面板，与对话管理/临时问答抽屉同款同位、同一时间互斥打开。抽屉内 Tab 分「进行中 / 已完成」两段：进行中按队列位次编号，一次只执行一个任务、其余按顺序排队；已完成按完成先后编号沉淀。行内不重复展示所属系统（所属关系由入口承载），队列抽屉只承载后台队列任务，同步任务不出现在抽屉中。已完成任务如带后续步骤（如产物验收），条目上提供入口按钮，点击在主会话启动对应工作流。

启动测试和非功能测试属于独立的“非功测试工作流”，但不进入“测试用例”目录。业务用例生成中时，目录使用进行中状态点；未生成的单条用例置灰且不可点击，生成完成后才可逐条查看，执行器运行后将结果更新为执行中、通过或失败。测试阶段不生成测试报告文件。

异步任务系统使用常规算力队列，潮汐任务系统使用低优先级的闲时队列；单条用例依次经过排队、生成、校验三个时段。潮汐系统的总时长刻意长于开发阶段演示时长，用于呈现“开发产物已全部完成，测试用例仍在后台生成”的排队效果。生成节奏由演示常量统一控制，两套系统仅节奏与算力口径不同，交互结构完全一致。

开发产物全部完成且最后一条 Workflow 收尾后，进入测试阶段弹框立即出现，不再额外等待用例准备任务；若用例仍在后台生成，弹框展示当前生成进度并提示可先进入测试阶段，未生成的单条用例在目录中置灰不可用。

用例生成失败或失效时，右侧用例内容区提供重新生成入口；同一时间不叠加测试用例工作台与辅助抽屉。

测试工作流按目录顺序逐条推进时，必须等当前用例在后台生成队列中就绪才会出现执行确认卡；未就绪期间不产生执行状态、不生成用例 Workflow，右侧目录保持置灰。

## 八、阶段准入

阶段是否可查看、是否具备进入条件和当前正在执行哪个阶段必须分开记录。

开发进入测试至少要求：

- 当前开发对象清单全部完成（完成以用户在待验收中接受产物为准）；
- 后台实现任务的构建与单元检查通过（随任务到达待验收即视为通过）；
- 开发阶段单元测试、联调、构建和基础启动检查通过；
- 当前 revision 的业务测试用例总量已确定；未生成的用例在测试工作台中置灰，生成后再开放查看和执行。

测试进入审查至少要求：

- 全部必需用例执行完成；
- 不存在未关闭的阻塞缺陷；

测试发现缺陷时，受影响开发对象回到“进行中/待修复”，但不得抹掉其曾经完成开发的历史。修复后重新执行受影响用例及必要的应用级验证。

## 九、右侧工作区与版本规则

右侧按阶段提供“开发产物”“测试用例”“应用文件”和必要时的“浏览器”能力。“应用文件”在每个阶段始终可用，作为统一项目文件管理系统，汇总已生成的项目文档与已接受的源码；需求规格说明书、UI 清单和技术规划方案在其中只读查看。开发阶段默认进入“开发产物”，测试阶段默认进入“测试用例”，这两个阶段都不提供浏览器 Tab；需求分析/项目计划也不提供浏览器 Tab。开发产物和测试用例都采用“目录 + 内容”双栏，目录宽度受控，层级可折叠，右侧根据当前叶子对象展示页面预览、接口调试或用例详情。只有技术规划方案确认后，顶部开发阶段旁才显示开发产物完成比例，顶部测试阶段旁才显示预计用例生成数量；确认前两个数字均不出现。开发目录中的产物展示领域状态点：未开始（灰）、实现排队（空心紫）、实现中（紫色呼吸）、待验收（紫点外圈光晕）、已完成（绿）、失败（红）；待验收页面即可在内容区打开预览，验收完成后保持可预览。测试目录中的用例展示生成状态点；同一版本内已确认完成的产物状态只增不减，目录刷新或下一条 Workflow 不得回退完成数。点击对象只选择当前 Workflow 或测试执行对象，不切换阶段主对话。开发阶段不再出现代码 Diff 授权页签；审查报告的 Diff 确认可临时切换到“应用文件”。应用文件使用同一源码编辑/只读视图；Markdown 文档不自动切换预览态，阶段主对话始终保持不变。

版本生成后固化当前资产快照并锁定为只读。只有需求和计划有效、开发对象完成、测试门禁通过、审查通过且用户明确验收通过时，才允许生成版本。历史版本不恢复写入型 Workflow，也不允许临时问答获得写权限。

## 十、关键旅程

### 新建应用

新建旅程的工作区目录必须与预置演示应用互斥：mock 目录选择器始终给出全新目录，手动输入预置演示应用的路径会被“已有 AIStudio 应用目录不能复用”拦截；应用索引按工作区路径去重、预置应用优先，因此最近项目里 v1.3 存量应用始终只有一条，专用于演示回退旅程。

创建迭代版本 → 需求分析主对话确认需求文档 → 项目计划主对话确认项目计划并启动后台用例生成 → 开发任务中 `@` 选择产物、确认详细设计并派发实现任务、验收待验收产物 → 进入测试主对话检查已生成用例并持续等待其余用例 → 用例测试 DAG 执行、修复缺陷并回归 → 审查主对话确认审查报告 → 用户验收 → 生成只读版本。

### 多产物开发

进入开发阶段 → 研发 Agent 投放一次 `@` 选择引导 → 用户输入 `@` 从候选中选“我的回检”并发送 → 当前任务投放该页面的模板选择卡 → 用户确认模板 → 前台 Workflow 完成详细设计并在轨迹末尾挂出「选择执行方式」节点 → 用户在内嵌选择卡上选“同步任务 / 异步任务 / 潮汐任务”：选后台通道则在对应任务系统派发后台实现任务、会话锁立即释放；选同步任务则当场在任务内播完生成节点并把记录沉淀到异步系统 → 用户可切到另一条开发任务（或继续在当前任务）`@` “回检介绍”发起下一个产物 → 两套任务系统并行、系统内串行地执行 Build DAG、代码生成、构建/单测和产物审查 → 任务完成后条目提供「验收」入口 → 点击在发起它的任务启动验收工作流，右侧打开产物审查、任务中确认验收 → 产物标记完成；两条实现任务完成后开发门禁开放。全过程不向任务插入迟到的完成通知，产物完成也不会自动触发下一张模板卡——下一个产物始终由用户 `@` 发起。

### 临时问答

用户打开左侧「任务管理」→ 切换到「临时问答」→ 只读询问当前文件或产物 → 返回任务管理切换回开发任务；如果需要修改，生成任务建议并转交开发任务用 `@` 选择产物，临时问答本身不执行 Workflow。

### 异步测试准备

需求规格说明书确认 → 顶部测试阶段显示生成数量 → 用户在开发过程中按需打开“测试用例”Tab查看分组进度 → 后台分批生成和校验 → 用例可逐条查看 → 开发门禁完成后进入测试 → 确定性执行全部用例并记录结果与缺陷。

## 十一、通用交互原则

**过程互动在对话区，右侧面板只承载静态与终态信息。** 用户的交流是连续的，一切操作类的过程互动（选择、授权、确认推进等）都以对话区卡片为主要载体；右侧面板是补充信息的呈现位，尽量只放静态信息与终态信息（产物审阅、预览、完成态）。例如 UI 设计稿的“选模板”在对话区确认卡内逐页完成（展开低保真线框翻看候选、“使用此模板”记录选择，全部选定后统一后台重画），右侧仅保留静态预览与已确认标记，不设第二套确认入口。UI 设计稿的模板预览使用低保真线框（与开发阶段同一模板目录，但只画版式骨架、损失视觉细节）——设计稿阶段只定结构、不定像素。

**禁用态是静态视觉行为，不是悬停后的反馈。** 控件不可用时必须第一时间以静态样式直接呈现——置灰、去强调、去除可点击观感（参照历史澄清卡的按钮、选项与输入框整体灰化）。禁止用鼠标悬停后才出现的信号表达不可用：光标形态切换（如 `not-allowed`）和悬停提示都是滞后的设计，不作为禁用的呈现手段，禁用控件保持默认光标。判断标准：不移动鼠标、不触发悬停，用户扫一眼界面就能分辨哪些可操作、哪些不可操作。
